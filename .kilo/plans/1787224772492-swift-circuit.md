## Part 1 — Cross-OS catalog doubles (server-only, migration 024)

**Method:** merge catalog rows by **normalized display name** (`app_name` → lowercase,
strip non-alphanumerics). Display names are OS-independent, so this covers every tool
category and every OS flavor (Linux/.desktop incl. Parrot/Kali, Windows Start-Menu,
macOS bundles). Rejected alternative: merging by `binary_name` (evidence: same binary
→ many products: `libreoffice`→6 apps, `flatpak`→Floorp+Warpinator, `gapplication`→
Maps+Weather, `OfficeClickToRun`→M365+Office2019, `OUTLOOK`→Outlook+Outlook classic,
`software-properties-gtk`→Additional Drivers+Software & Updates; also misses Google
Chrome `chrome` vs `google-chrome-stable`).

Caveats (honest): (1) two unrelated products sharing the exact display name would
wrongly merge (rare); (2) same product with genuinely different display names across
OSes won't merge (rare — client already normalizes e.g. "Microsoft Visual Studio Code
(User)").

### Steps
1. **Migration `024_catalog_merge.sql`** (one transaction, idempotent):
   - key = `regexp_replace(lower(app_name), '[^a-z0-9]', '', 'g')`
   - group non-deleted rows having `count(*) > 1`
   - winner = most `employee_installed_applications` links, tie → earliest `created_at`
   - re-point `employee_installed_applications.installed_application_id` loser→winner
     (junction dedup via `ON CONFLICT (employee_id, installed_application_id) DO NOTHING`
     then delete the colliding duplicate link)
   - re-point `app_sessions.installed_app_id` loser→winner
   - carry loser's `type_id` / `category_id` onto the winner if the winner has none
   - soft-delete losers (`deleted_at = now()`) — keeps the UNIQUE `app_fingerprint`
     constraint intact
   - expected result on dev DB: 178 → ~171 rows, 7 doubles gone
2. **Sync hardening** — `server/internal/repository/new_schema_repo.go`
   `UpsertApplicationCatalog`: before INSERT, look up an existing non-deleted row by
   normalized `app_name`; if found reuse it (link employee to it) instead of creating a
   new fingerprint row. Stops future Linux/Windows syncs re-creating doubles.
3. Verify: `go build` / `go vet` / `go test` clean; apply migration to dev DB; smoke
   test a live sync + the Apps page.

## Part 2 — `xdg-dbus-proxy` label on Floorp (client)

**Root cause (verified live):** catalog row is correct (`Floorp` / binary `flatpak` /
`one.ablaze.floorp`). Bad label is the browser tracker's runtime `ProcessName` (shown as
the browser/source badge on Web Activity, used for app-session lookups). Flatpak
registers the window with AT-SPI under the **`xdg-dbus-proxy` PID**, which has **no
`FLATPAK_ID`** in its environ (live: PID 53874 has only `DBUS_SESSION_BUS_ADDRESS`), so
`resolve_app_name(pid)` — which reads only that PID's own environ — falls back to
`/proc/comm` = `xdg-dbus-proxy`. Real app (PID 53878, `FLATPAK_ID=one.ablaze.floorp`) is a
sibling under the same bwrap root (`bwrap --args 41 -- floorp`).

Process tree (live): `gnome-shell(2712) → bwrap(53844) "bwrap --args 41 -- floorp"`
→ `bwrap(53873) → xdg-dbus-proxy(53874)`, and `→ bwrap(53877) → floorp(53878)`.

### Steps
1. **Extend `resolve_app_name(pid)`** in the embedded Python probe of
   `client/Core/BrowserAccessibility/LinuxAtSpiBrowserReader.cs` (~line 454):
   - if own environ has no `FLATPAK_ID`, walk **up the PPID chain through `bwrap`** to
     the flatpak root (top-most `bwrap` whose parent is not `bwrap`)
   - DFS that root's descendants for a process with `FLATPAK_ID` → use its short name
   - fallback: parse the root's cmdline `bwrap --args N -- <name>` → `<name>`
   - `bwrap`/`xdg-dbus-proxy` are flatpak's OS-level sandbox binaries (structural, no
     product names) → No-Hardcoded-Names Rule compliant
   - C# `ReadComm`/`_pidNameCache` is fed from probe results → fixed automatically
2. **Optional nicety:** `InstalledAppDetector` stores the flatpak short id (`floorp`) as
   `binary_name` instead of `flatpak` (from `Exec=flatpak run <id>`), so binary lookups
   match too. (Fuzzy lookup already matches Floorp via `app_name`, so not required.)
3. **Installer-Parity:** `dotnet build` clean + verify in an installed build; ships in
   the next installer build.

## Phase 2 — Remove All Hardcoded Browser Names (Dynamic Browser Detection)

## 1. Goal

Totally remove every hardcoded browser product name (`chrome`, `firefox`, `edge`, `brave`,
`opera`, `vivaldi`, `chromium`, `safari`, `arc`, `iexplore`, `msedge`, `microsoft-edge`,
etc.) from the client and replace them with **structural / OS-metadata-driven detection**
plus a **dynamic browser registry** sourced from `installed_applications.is_browser`. This
makes the tracker automatically recognize any new browser (Floorp, LibreWolf, Waterfox,
Arc, Zen, etc.) without a code change or redeploy.

## 3. What Is Already Dynamic (Keep As-Is)

The **installed-applications inventory** already classifies browsers dynamically using genuine OS metadata:
- **Linux**: `.desktop` `Categories=WebBrowser` or `MimeType x-scheme-handler/http(s)`
- **Windows**: registry `URLAssociations` http/https
- **macOS**: `CFBundleURLSchemes` containing both `http` and `https`

`installed_applications.is_browser` + `installed_applications.binary_name` + `installed_applications.app_name` are the **single source of truth** for "what is a browser on this machine."

`ActivityContextParser.ParseBrowserContext` already strips the browser suffix **dynamically** using `appDisplayName` — no hardcoded list.

## 4. Dynamic Detection Strategy

### 4.1 Runtime browser registry (`IBrowserRegistry`)

Add a new abstraction that knows "which processes are browsers" without any hardcoded names:

```csharp
public interface IBrowserRegistry
{
    bool IsBrowser(string processName);          // exact / fuzzy match against installed apps
    bool IsBrowser(string processName, string? commandLine);
    string? GetDisplayName(string processName);  // "Google Chrome" from installed_applications
    IEnumerable<string> GetAllBrowserProcessNames(); // for bulk operations
}
```

Implementation (`BrowserRegistry`) sources from `IInstalledAppDetector` + a cached refresh:
- On init + every 5 min, scan `InstalledAppDetector.GetAllInstalledApplications()` for `IsBrowser == true`
- Build a `Dictionary<string, InstalledApplication>` keyed by `binary_name` (case-insensitive) and `app_name`
- `IsBrowser(name)` → exact match, then case-insensitive contains-match (≥4 chars both sides, same fuzzy rule already used in `InstalledAppDetector.ResolveDisplayName`)
- `GetDisplayName(name)` → returns the human-readable name (e.g. `"Google Chrome"`, `"Floorp"`) for suffix stripping

Register as `Singleton` in DI. The browser tracker, readers, history reader, session label resolver, and LogCollectorService all receive it via constructor injection.

### 4.2 Eliminate `BrowserProcessHints` / `IsBrowserProcess` static helper

- Remove `BrowserProcessHints` and `IsBrowserProcess()` from `BrowserAccessibilityHelpers`
- Replace every call site with `IBrowserRegistry.IsBrowser(processName, commandLine)`
- `BrowserAccessibilityHelpers` retains only `NormalizeUrl`, `ExtractDomain`, `TitleSuggestsIncognito`, `StableInt32`

### 4.3 Eliminate hardcoded `StripBrowserSuffix` list

- `StripBrowserSuffix` becomes:
  ```csharp
  public static string StripBrowserSuffix(string title, string? appDisplayName)
  {
      if (string.IsNullOrWhiteSpace(title)) return string.Empty;
      if (string.IsNullOrEmpty(appDisplayName)) return title.Trim();
      var suffix1 = $" - {appDisplayName}";
      var suffix2 = $" — {appDisplayName}";
      // strip whichever suffix is present
      ...
  }
  ```
- Every call site passes the dynamic `appDisplayName` from `IBrowserRegistry.GetDisplayName()` or from the snapshot / installed-app lookup.
- The old 10-entry hardcoded suffix list is deleted.
- `ActivityContextParser.ParseBrowserContext` already does this correctly — it becomes the canonical implementation; `BrowserAccessibilityHelpers.StripBrowserSuffix` becomes a thin wrapper.

### 4.4 Linux Python probe — remove `BROWSER_HINTS`

The probe already builds `_browser_exes` by scanning `.desktop` files for `Categories=WebBrowser` (cached 5 min on disk). Remove the `BROWSER_HINTS` tuple and the `any(h in comm for h in BROWSER_HINTS)` / `any(h in cmd for h in BROWSER_HINTS)` checks. Replace with:

```python
is_browser = comm in _browser_exes
```

For the Firefox sessionstore branch, replace `read_comm(int(pid)) == 'firefox'` with a check against `_browser_exes`:

```python
if read_comm(int(pid)) in _browser_exes:
    ff_pid = int(pid)
    break
```

This automatically includes any browser that has a `.desktop` file with `Categories=WebBrowser` — Floorp, LibreWolf, Waterfox, etc. are all picked up without a Python code change.

### 4.5 Session label resolver — dynamic browser check

Replace the hardcoded switch:

```csharp
public static string? Resolve(string processName, int rootPid)
{
    // OLD: hardcoded switch on processName
    // NEW: ask the browser registry
    if (!_browserRegistry.IsBrowser(processName)) return null;
    // Chromium-family: --profile-directory=...
    // Firefox: -P / --profile...
    // Fallback: --user-data-dir basename
    ...
}
```

The profile-extraction logic (`--profile-directory`, `-P`, `--user-data-dir`) is browser-family-agnostic — it works for ANY Chromium-based browser and ANY Firefox-based browser. The only hardcoded part was the gate that decided *whether* to run it.

### 4.6 Browser history reader — dynamic family + dynamic profile discovery

**`ResolveFamily`** — replace hardcoded substring matching with a check against `IBrowserRegistry`:
- If `IsBrowser(processName)` → determine family by checking if the browser's display name or binary name matches known Chromium-family or Firefox-family patterns **derived from the installed app's metadata** (e.g., `Categories`, `DesktopId`, `bundle_id`).
- Simpler: the history DB itself reveals the family. Chromium-family browsers use `History` (SQLite, `urls` table); Firefox uses `places.sqlite`. The `ProfileState.Family` is already determined by which DB file is found. `ResolveFamily` is only needed to filter visits by family — if we can't determine family from the process name, we can just skip the filter and search all visits.

**Profile path discovery** — the hardcoded paths in `EnumerateCandidates()` can stay as **seeds** (they cover 99% of installs), but add a dynamic scan:
- On Linux: scan ALL directories under `~/.config/` that contain a `History` or `places.sqlite` file (cheap shallow scan)
- On Windows: scan `%LocalAppData%` subdirectories for `User Data\Default\History`
- On macOS: scan `~/Library/Application Support` for `History` / `places.sqlite`
- This makes brand-new browsers (Zen, Floorp, etc.) discoverable without hardcoding their folder names.

**Firefox detection in `DiscoverProfilesLocked`** — instead of checking `profile.Family == "firefox"`, check the DB schema (`places.sqlite` has `moz_places`; `History` has `urls`). The family label is metadata we attach; the actual DB structure tells us what format it is.

## 6. What We Keep (Structural Exceptions)

Per the **No-Hardcoded-Names Rule** already codified in `AGENTS.md` §6, these are **allowed** because they are OS-shell constructs, not user-software names:
- Linux GNOME daemon prefixes in `NonAppProcesses` / `NonAppProcessPrefixes`
- Windows shell display-name overrides (`explorer` → `File Explorer`, `svchost` → `Windows Services`)
- Windows Update `KB`-prefix naming convention
- Installer filename conventions (`unins*`, `*setup*`, `*installer*`)
- Chromium `--type=` subprocess flags (structural, same across all Chromium-family browsers)
- Firefox `--contentproc` flag (structural)

These are **not** browser product names — they are OS/metadata conventions that apply universally.

## 8. Risk / Tradeoffs

- **Startup timing**: `IBrowserRegistry` caches from `installed_applications`, which is scanned at startup. The browser tracker starts after a short delay; the first poll will see the cached list. Acceptable.
- **Windows Start Menu shortcuts without registry entries**: portable / non-installed browsers that only have a Start Menu shortcut will initially have `is_browser=false`. They will be correctly classified once the registry scan runs and merges, OR we can add a one-time post-scan pass that checks URL associations for all detected apps.
- **Profile path discovery**: the dynamic shallow scan under `~/.config/`, `%LocalAppData%`, etc. is slightly more expensive than hardcoded paths, but it runs on a 15-second cadence and only scans top-level subdirectories — negligible cost.

## 9. Out of Scope

- **macOS browser detection via bundle inspection** is already dynamic (`CFBundleURLSchemes`) — no change needed.
- **Server-side changes** — none. The `is_browser` column already exists on `installed_applications`.
- **Web dashboard changes** — none. Browser display names come from the server.

### Corrections applied to plan

1. **`IBrowserRegistry` must be registered unconditionally** — `LogCollectorService` and `SessionLabelResolver` use it regardless of `ALPHA_BROWSER_TRACKING_ENABLED`. Register as `Singleton` in `Program.cs` outside the `if (config.BrowserTrackingEnabled)` block.

2. **`MacOsAccessibilityBrowserReader` needs display names, not process names** — its AppleScript filters by the macOS process name (which equals the display name, e.g. "Google Chrome"). Add `IReadOnlyList<string> GetAllBrowserDisplayNames()` to `IBrowserRegistry`. The macOS reader builds its AppleScript list from this method.

3. **`StripBrowserSuffix` call sites in `LinuxAtSpiBrowserReader`**:
   - `TitlesOverlap` (line 985) calls `StripBrowserSuffix` without a display name → pass `null` (no-op, keeps title as-is).
   - `IndexWmWindows` (line 323) strips for dedup → make it non-static, look up display name via `_browserRegistry.GetDisplayName(ReadComm(w.Pid))`, pass it to `StripBrowserSuffix`. If no display name, skip stripping (raw-title dedup is safe because `TitlesOverlap` later handles it).

4. **`BrowserHistoryReader.TryResolveUrl`** — remove `ResolveFamily()` entirely. Searching all visits without a family filter is safe because exact-title match is the primary signal and cross-family title collisions are vanishingly rare. This eliminates the need to determine "chromium vs firefox" from the process name.

5. **`BrowserHistoryReader` profile discovery** — the generic `FindGenericChromiumProfiles` / `FindGenericFirefoxProfiles` already exist and are already called for all three platforms. The hardcoded paths are redundant seeds. No new code needed; the plan's "add dynamic scan" is already implemented.

6. **`InstalledAppDetector.ScanStartMenuShortcuts`** — set `isBrowser = false` for Start Menu shortcuts. The subsequent registry scan (`ScanRegistryUninstallNode`) already merges onto the same row and sets `IsBrowser = true` when URL associations are present. No circular dependency on `IBrowserRegistry`.

7. **`SessionLabelResolver`** — keep it static, add `IBrowserRegistry` as a parameter to `Resolve()`:
   ```csharp
   public static string? Resolve(string processName, int rootPid, IBrowserRegistry browserRegistry)
   ```
   Update the single call site in `LogCollectorService` to pass `_browserRegistry`. No constructor change needed.

8. **`AccessibilityBrowserReaderFactory.Create`** — remains static. Change signature to accept `IBrowserRegistry` + `IInstalledAppDetector`:
   ```csharp
   public static IAccessibilityBrowserReader Create(ILoggerFactory loggerFactory, IBrowserRegistry browserRegistry, IInstalledAppDetector appDetector)
   ```

   Update the `Program.cs` call site to pass both.

9. **Thread safety of `BrowserRegistry`** — use double-checked locking: volatile read of `_browserNames` for the fast path, `lock(_gate)` only on stale refresh. `IsBrowser()` is called per-process per-cycle (~200 calls/30s); lock-free fast path keeps overhead negligible.
