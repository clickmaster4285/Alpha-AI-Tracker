================================================================================
  BUG #1 — Systemd Service File Never Created (Infinite Permission Wizard Loop)
================================================================================

SEVERITY: HIGH
AFFECTS: All fresh Linux installs (Ubuntu AND Mint)
MASKED ON: Ubuntu (GNOME's XDG autostart is reliable enough without systemd)

DESCRIPTION:
  On a fresh install, the permission wizard's "Background Running" step (Step 2)
  can NEVER be completed. The user is stuck in an infinite loop where Step 2
  always re-appears, even after clicking "Grant".

ROOT CAUSE:
  The flow is:

  1. User clicks "Grant" on Step 2 (BackgroundRunning)
  2. MainViewModel.GrantBackgroundRunningAsync() is called
     (MainViewModel.cs:863-868)
  3. It calls _autoStart.EnableAutoStartForced()
     (AutoStartService.cs:58-112)
  4. EnableAutoStartForced() does TWO things:
     a) Creates the .desktop autostart file  <-- this works
     b) Runs: systemctl --user enable alpha-ai-tracker.service
  5. BUT the .service FILE does not exist yet!
     The ONLY place that creates it is:
       BackgroundGuardService.InstallSystemdServiceAsync()
       (BackgroundGuardService.cs:169-261)
     And it is GUARDED by:
       if (_systemdWasInstalled && _systemdServiceName != null)
       (BackgroundGuardService.cs:100)
     On a fresh install, _systemdWasInstalled = false
     (set at line 53 via DetectSystemdService() which checks file existence)
     So InstallSystemdServiceAsync() is NEVER called.
  6. systemctl --user enable fails silently (exit code ignored, caught at line 106)
  7. GetNextPermissionStep() re-evaluates:
     - IsAutoStartEnabled() = YES (.desktop file exists) -> passes
     - IsBackgroundGuardConfigured() = NO (.service file doesn't exist) -> FAILS
     - Returns PermissionStep.BackgroundRunning -> STEP 2 AGAIN -> INFINITE LOOP

  The .service file is only created by BackgroundGuardService, but the guard
  only runs AFTER the host starts (line 208 in Program.cs). And even then, it
  only creates the file if it WAS previously installed and got deleted.

AFFECTED FILES:
  - client/ViewModels/MainViewModel.cs:863-868 (GrantBackgroundRunningAsync)
  - client/Services/AutoStartService.cs:58-112 (EnableAutoStartForced)
  - client/Services/BackgroundGuardService.cs:100-110 (watchdog guard)
  - client/Services/BackgroundGuardService.cs:169-261 (InstallSystemdServiceAsync)

================================================================================
  BUG #3 — Stale Mutex Blocks Background Launch After Crash/Reboot
================================================================================

SEVERITY: HIGH
AFFECTS: Linux Mint 22.2 (and potentially all platforms)

DESCRIPTION:
  The global named mutex "AlphaAITracker" (Program.cs:73) is used for
  single-instance enforcement. When the app starts with --background, it
  checks if the mutex is already held:

    if (!mutexCreated)
    {
        if (isUserLaunch)
            SingleInstanceService.SignalExistingInstance();
        return;  // <-- EXITS SILENTLY (line 105)
    }

  Problem: If the previous instance crashed, was force-killed, or the system
  was rebooted without clean shutdown, the mutex MAY still appear held (OS-
  dependent behavior). The new --background launch sees the mutex as taken,
  determines it's NOT a user launch, and exits immediately without starting
  any tracking services.

  On Ubuntu/GNOME, session cleanup is more reliable and this rarely happens.
  On Linux Mint/Cinnamon, force-closing via the task manager or rebooting
  during heavy load can leave the mutex orphaned.

  The --restart flag (line 81-91) has a WaitOne(8s) timeout, but that's only
  for the explicit restart flow, not for normal --background auto-start.

AFFECTED FILES:
  - client/Program.cs:73-106 (mutex handling)


================================================================================
  BUG #4 — Cinnamon Autostart Reliability Gap
================================================================================

SEVERITY: LOW-MEDIUM
AFFECTS: Linux Mint 22.2 (Cinnamon desktop)

DESCRIPTION:
  The .desktop autostart file at ~/.config/autostart/alpha-ai-tracker.desktop
  uses X-GNOME-Autostart-enabled=true. While Cinnamon IS XDG-compliant and
  should honor this, there are known reliability differences:

  1. Cinnamon's startup applications manager may not immediately recognize
     manually-created .desktop files (vs files added through its GUI).

  2. Cinnamon session (cinnamon-session) may start autostart entries BEFORE
     the user's D-Bus session is fully ready, causing the app to fail to
     connect to its named pipe or log store.

  3. If Linux Mint 22.2 defaults to Wayland (not X11), the autostart timing
     may differ from X11 sessions.

  4. The .desktop file format is correct per XDG spec, but Cinnamon may
     have subtle parsing differences from GNOME's gnome-session.

AFFECTED FILES:
  - client/Services/AutoStartService.cs:258-281 (EnableLinuxAutoStart)


================================================================================
  HOW EACH FIX SHOULD BE APPLIED
================================================================================

NOTE: No code changes made yet. This is the plan only.

FIX #1 — Create systemd service file before enabling it
-------------------------------------------------------
  WHERE: client/ViewModels/MainViewModel.cs:863-868

  WHAT: GrantBackgroundRunningAsync() should call a new method that:
    1. Creates the .service file at ~/.config/systemd/user/alpha-ai-tracker.service
       (same content as BackgroundGuardService.InstallSystemdServiceAsync, line 174-190)
    2. Runs "systemctl --user daemon-reload"
    3. Runs "systemctl --user enable alpha-ai-tracker.service"
    4. Runs "systemctl --user start alpha-ai-tracker.service"

  WHY: Currently, GrantBackgroundRunningAsync() delegates to
  EnableAutoStartForced() which tries "systemctl --user enable" without the
  file existing. The service file must be created FIRST.

  ALSO: Update the BackgroundGuardService.ExecuteAsync() initial detection
  (line 53) so that on a fresh install, if the .desktop autostart file exists
  but the .service file doesn't, the guard proactively creates it. This makes
  the guard work as both a watchdog AND a first-time installer.


FIX #2 — Fix EnableAutoStartForced() to check systemctl exit code
-----------------------------------------------------------------
  WHERE: client/Services/AutoStartService.cs:89-97

  WHAT: After the process exits, check proc.ExitCode. If non-zero, log the
  error and return false (or at minimum, read StandardError for the message).

  WHY: Currently the exit code is completely ignored, masking the fact that
  the service file doesn't exist.


FIX #3 — Add mutex stale-detection for --background launches
------------------------------------------------------------
  WHERE: client/Program.cs:73-106

  WHAT: When the mutex is held and the launch is --background (NOT a user
  launch), instead of exiting silently, check if the existing process is
  actually alive:

    1. Use Process.GetProcessesByName("client") to find running instances
    2. If no other process is found, the mutex is stale (orphaned)
    3. Release the stale mutex and re-acquire it
    4. Proceed with normal startup

  Alternatively, use a more robust single-instance mechanism:
    - Check /proc/<pid>/status for the owning PID
    - Use a lockfile with PID written inside (can detect stale locks)
    - Add a mutex lease timeout (auto-release after N seconds of inactivity)

  WHY: On Linux Mint/Cinnamon, force-kills and reboots can leave the mutex
  orphaned. The --background auto-start then fails silently every boot until
  the user manually kills the orphaned process or reboots cleanly.


FIX #4 — Add systemd service as primary auto-start on Cinnamon
--------------------------------------------------------------
  WHERE: client/Services/AutoStartService.cs:258-281

  WHAT: On Linux, after creating the .desktop file, ALSO ensure the systemd
  user service is installed and enabled. This makes the systemd service the
  PRIMARY auto-start mechanism (in addition to the .desktop file as a backup).

  The systemd user service is independent of the desktop environment and works
  identically on GNOME, Cinnamon, KDE, XFCE, etc. It also survives desktop
  session restarts (if lingering is enabled).

  Add "loginctl enable-linger $USER" if not already enabled (one-time setup).
  This ensures the systemd user instance persists beyond login sessions.

  WHY: Relying solely on XDG autostart is fragile across different desktop
  environments. The systemd service provides a consistent, DE-agnostic
  auto-start mechanism.

================================================================================
  SUMMARY
================================================================================

Bug #1 (Infinite Wizard Loop) is the PRIMARY reason auto-start doesn't work
on Linux Mint 22.2. The user gets stuck on Step 2 and may abandon the setup
process. Even though the .desktop file IS created in Step 1, the user may not
realize it.

Bug #3 (Stale Mutex) is the SECONDARY reason. Even if the .desktop file exists
and Cinnamon tries to launch the app at login, the background instance may
exit silently due to an orphaned mutex from a previous session.

Bug #4 (Cinnamon Reliability) is a CONTRIBUTING factor. Cinnamon's autostart
is less battle-tested than GNOME's, so even a correctly configured .desktop
file may not launch reliably.

On Ubuntu, Bug #1 exists but is masked because GNOME's XDG autostart is
reliable enough that the .desktop file alone (created in Step 1) handles
auto-start without needing the systemd service.

  BUG #5 — Shift Management: Soft-Deleted Shift Names Block Re-Creation
  Date Found: 2026-08-29
  Environment: Web Dashboard (Shift Management page)
================================================================================

SEVERITY: MEDIUM
AFFECTS: Web dashboard shift management CRUD

DESCRIPTION:
  When creating a shift, deleting it, then recreating a shift with the same
  name, the server either rejects it or silently renames it — even though
  the old shift is soft-deleted (deleted_at IS NOT NULL).

  Steps to reproduce:
    1. Create a shift named "morning" — succeeds
    2. Delete the "morning" shift — soft-deleted (deleted_at set)
    3. Create a new shift named "morning" — should succeed (old one is deleted)
       BUT it either fails with a uniqueness error or the name is changed

ROOT CAUSE:
  The server-side UNIQUE constraint on the shift name column does NOT
  exclude soft-deleted rows. The constraint is something like:

    UNIQUE (name)  -- or  UNIQUE (name, deleted_at)

  This means a soft-deleted row with name="morning" still occupies the
  uniqueness slot, so a new INSERT with name="morning" violates the
  constraint.

  The correct behavior: only enforce uniqueness among NON-deleted rows.
  This can be implemented as either:
    a) A partial unique index:  CREATE UNIQUE INDEX ... WHERE deleted_at IS NULL
    b) A unique constraint on (name, deleted_at) — but only if deleted_at
       is always NULL for active rows (fragile, not recommended)

EXPECTED BEHAVIOR:
  After soft-deleting a shift, the name should be freed so a new shift
  with the same name can be created without conflict.

AFFECTED FILES:
  - server/migrations/ (shift table UNIQUE constraint)
  - server/internal/repository/new_schema_repo.go (shift CRUD)
  - server/internal/handler/ (shift handler)
  - web/src/app/(app)/settings/shift-management/page.tsx (UI)

  BUG #6 — installed_applications: version and publisher always empty on Linux
  Date Found: 2026-08-31
  Environment: Linux (Ubuntu, Mint, all distros)
  Works On: Windows (registry populates version/publisher correctly)
================================================================================

SEVERITY: MEDIUM
AFFECTS: All Linux installed builds — every application row in the SQLite
         installed_applications table has empty app_version and publisher

DESCRIPTION:
  Every installed application on Linux has empty app_version and publisher
  fields in the installed_applications SQLite table. This data IS available
  from the OS (dpkg-query, flatpak, snap) but is never written into the
  installed_applications table on Linux.

  Evidence from the live DB at /home/devteam/.local/share/alpha-ai-tracker/data/alpha_tracker.db:

    sqlite> SELECT COUNT(*) FROM installed_applications WHERE is_installed=1;
    101

    sqlite> SELECT COUNT(*) FROM installed_applications
            WHERE is_installed=1
              AND (app_version = '' OR app_version IS NULL);
    101

    sqlite> SELECT COUNT(*) FROM installed_applications
            WHERE is_installed=1
              AND (publisher = '' OR publisher IS NULL);
    101

  100% of rows have empty version and publisher. The sync payload
  (SyncService.cs:276-277) DOES include appVersion and publisher fields,
  but they are always empty strings, so the server stores empty values too.

ROOT CAUSE:
  On Linux, InstalledAppDetector.ScanDesktopFiles() (InstalledAppDetector.cs:379-391)
  creates InstalledApplication entries from .desktop files with hardcoded empty
  strings:

    _installedApps.Add(new InstalledApplication
    {
        AppName = name,
        BinaryName = binaryName ?? "",
        DesktopId = Path.GetFileNameWithoutExtension(filePath),
        Categories = categories ?? "",
        InstallPath = exec ?? filePath,
        Publisher = "",          // <-- HARDCODED EMPTY
        AppVersion = "",         // <-- HARDCODED EMPTY
        ChangeType = "seen",
        IsBrowser = isBrowser,
        DetectedAt = DateTime.UtcNow,
    });

  This is correct behavior for .desktop files — they do NOT contain version
  or publisher metadata. However, the data IS available from other OS sources:

  Source 1 — dpkg-query (PackageDetector.ScanDpkg, PackageDetector.cs:260-317):
    dpkg-query -W -f='${Package}\t${Version}\t${Maintainer}\n'
    Returns 2697 packages with version + maintainer (publisher).
    BUT this data goes into installed_packages table, NOT installed_applications.

  Source 2 — flatpak (PackageDetector.ScanFlatpak):
    flatpak list --columns=name,application,version
    Returns version for Flatpak apps (Floorp, Warpinator, etc.).
    BUT this data also goes into installed_packages only.

  Source 3 — snap (PackageDetector.ScanSnap):
    snap list — returns version + publisher.
    BUT again, installed_packages only.

  The SoftwareClassifier (SoftwareClassifier.cs:158-173) has MergeAppMetadata()
  that copies version/publisher between InstalledApplication rows, but it only
  merges between app-to-app sources (e.g., registry metadata into shortcut rows
  on Windows). There is NO code path that merges installed_packages data into
  installed_applications on Linux.

  The two tables are SEPARATE:
    installed_applications  — populated by InstalledAppDetector (from .desktop files)
    installed_packages      — populated by PackageDetector (from dpkg/npm/pip/...)

  On Windows, version/publisher come from the registry (InstalledAppDetector
  reads them directly), so the fields are populated. On Linux, .desktop files
  are the ONLY source for installed_applications, and they lack this metadata.

  THE GAP: No cross-reference exists to look up a binary_name or package name
  in the dpkg database and copy its version/publisher into the matching
  installed_applications row.


AFFECTED FILES:
  - client/Core/InstalledAppDetector.cs:379-391 (ScanDesktopFiles — hardcodes empty)
  - client/Core/PackageDetector.cs:260-317 (ScanDpkg — has the data but writes to wrong table)
  - client/Core/SoftwareClassifier.cs:158-173 (MergeAppMetadata — only merges app-to-app)
  - client/Storage/SqliteLogStore.cs:467-468,1021-1042 (INSERT/UPDATE — stores empty strings)

  RESOLUTION PLAN FOR BUG #6
================================================================================

NOTE: No code changes made yet. This is the plan only.

FIX #6 — Cross-reference dpkg/flatpak/snap data into installed_applications
---------------------------------------------------------------------------

  OPTION A (Recommended) — Post-scan enrichment pass in InstalledAppDetector:

    WHERE: client/Core/InstalledAppDetector.cs, new method after
           ScanDesktopFiles() completes

    WHAT: After all .desktop files are scanned and _installedApps is populated,
    run a enrichment pass that:

    1. Build a lookup dictionary from dpkg-query:
       dictionary<string, (string version, string publisher)> dpkgLookup
       Key = package name (e.g., "google-chrome-stable", "vlc", "vim")

    2. For each InstalledApplication in _installedApps:
       a. Try exact match on binary_name against dpkg package name
       b. Try exact match on app_name against dpkg package name
       c. Try fuzzy match: dpkg package name contains binary_name or vice versa
       d. If matched AND app.AppVersion is still empty:
          - Set app.AppVersion = dpkgLookup[match].version
          - Set app.Publisher = dpkgLookup[match].publisher

    3. Same logic for flatpak apps:
       - flatpak app IDs are already the DesktopId (e.g., "org.x.Warpinator")
       - Match on DesktopId against flatpak application ID
       - Copy flatpak version into AppVersion

    4. Same logic for snap apps:
       - Match on binary_name or app_name against snap package name
       - Copy snap version and publisher

    WHY: This is the least invasive fix — it adds a post-scan enrichment step
    that only fills in EMPTY fields. It does not change the scan logic, the
    table schema, or the sync payload. Existing populated fields are never
    overwritten (the COALESCE NULLIF pattern in SqliteLogStore already protects
    updates).

    The dpkg data is already collected by PackageDetector.ScanDpkg() at the
    same startup phase. Either:
      a) InstalledAppDetector calls dpkg-query directly (duplicate but isolated)
      b) Share the dpkg data from PackageDetector via a static cache or DI

    Option (a) is simpler and avoids cross-component coupling. The dpkg-query
    call takes <50ms and runs once at startup.


  OPTION B — Merge at Store layer (SqliteLogStore):

    WHERE: client/Storage/SqliteLogStore.cs, StoreInstalledApplicationsAsync

    WHAT: When inserting/updating an installed_applications row, if app_version
    or publisher is empty, query the installed_packages table for a matching
    package and copy its version/publisher.

    WHY: This ensures ANY future code path that writes an InstalledApplication
    with empty version/publisher automatically gets enriched. The merge happens
    at the persistence layer, not the detection layer.

    DRAWBACK: Couples the two tables at the store level; makes the store aware
    of detection semantics.


  RECOMMENDED: Option A — it's cleaner, keeps the enrichment in the detection
  layer, and the dpkg-query call is cheap (<50ms on this machine with 2697
  packages).

  BUG #7 — Peripherals Page: Duplicate Devices Shown (Connected + Disconnected)
  Date Found: 2026-09-02
  Environment: Web Dashboard — Device Specs > Peripherals page
  Affects: All platforms
================================================================================

SEVERITY: MEDIUM
AFFECTS: Web dashboard peripherals page — every device with a connect/disconnect
         history shows TWO cards instead of one

DESCRIPTION:
  The peripherals page renders one card per hardware_devices row, including
  both the current (connected) row AND old disconnected rows. For example,
  a USB microphone with 2 history entries (plugged → unplugged → plugged)
  shows TWO cards:

    Card 1: "Microphone (3- USB Audio Device)" — Connected
    Card 2: "Microphone (3- USB Audio Device)" — Disconnected

  Same for "USB Composite Device", "Headset", etc. — every device that
  was ever unplugged and reconnected shows a duplicate card. The page
  currently renders ALL rows from hardwareDevices without grouping.

STEPS TO REPRODUCE:
  1. Plug in a USB device (e.g. microphone) — a Connected card appears
  2. Unplug it — the card shows Disconnected
  3. Plug it back in — a NEW Connected card appears
  4. Now the page shows TWO cards for the same device

ROOT CAUSE:
  web/src/app/(app)/device-specs/peripherals/page.tsx:29
  iterates over hardwareDevices.map() directly — every row in the
  hardware_devices table gets its own card. When a device is
  unplugged and replugged, the server creates a new row (new id,
  new plugged_at, unplugged_at set on the old row). The page
  displays BOTH rows independently.

  The data is correct (the table stores the full history), but the
  UI should group by device identity and show only ONE card per
  device, with the history accessible via an expand/collapse arrow.

EXPECTED BEHAVIOR:
  By default, show a SINGLE card per device (the most recent state).
  If the device has history (multiple connect/disconnect rows), show
  a chevron/arrow button that expands to reveal previous connect and
  disconnect events. The default view should always show the current
  state (Connected or Disconnected) as the top-level card.

AFFECTED FILES:
  - web/src/app/(app)/device-specs/peripherals/page.tsx (renders raw rows)


================================================================================
  RESOLUTION PLAN FOR BUG #7
================================================================================

NOTE: No code changes made yet. This is the plan only.

FIX #7 — Group hardware devices by identity, show history in expandable rows
---------------------------------------------------------------------------

  WHERE: web/src/app/(app)/device-specs/peripherals/page.tsx

  WHAT:

  1. GROUP rows by device identity:
     - Primary key: device.product + device.deviceClass + device.vendor
       (same product name, same class, same vendor = same physical device)
     - Fallback: if product is empty, use device.serial as identity
     - Grouping logic: reduce hardwareDevices into a Map<string, HardwareDevice[]>
       where the key is the identity and the value is the history sorted by
       pluggedAt descending (newest first)

  2. DEFAULT CARD — show only the most recent row per group:
     - Each group renders ONE card
     - The card shows: product name, vendor, device class, serial, pluggedAt
     - Status badge: Connected if unpluggedAt is null, Disconnected otherwise
     - If the group has only 1 row (no history), render as-is (no arrow)

  3. EXPANDABLE HISTORY — arrow button when history exists:
     - If the group has >1 row, show a small chevron (▼/▶) button in the
       top-right corner of the card
     - Clicking the arrow expands a sub-list below the card showing all
       historical rows (sorted by pluggedAt DESC)
     - Each history row shows: status (Connected/Disconnected), pluggedAt,
       unpluggedAt (if present), formatted with formatDateShort
     - The arrow button indicates "view history" — collapsed by default

  4. UI details:
     - Arrow button: lucide ChevronDown/ChevronRight, 16px, muted color,
       positioned next to the status badge
     - Expanded history: subtle left-border accent (e.g. border-l-2
       border-muted), slightly smaller text, indented under the card
     - Animation: smooth height transition when expanding/collapsing
       (framer-motion or CSS transition)
     - Empty history (single row): no arrow rendered, card is static

  WHY: The current UI shows raw table rows as cards, which is confusing
  when a device has history. The fix groups by device identity and makes
  history optional — the default view is clean (one card per device) and
  the history is available on demand. This matches the pattern already
  used on the App Usage page (expandable per-app session groups).

  BUG #8 — App Usage Duration: Multiplied When Multiple Tabs Open
  Date Found: 2026-09-02
  Environment: Web Dashboard — Employee Journey > App Usage page
  Affects: All platforms (Chrome/Edge/Brave with multiple tabs)
================================================================================

SEVERITY: HIGH
AFFECTS: Web dashboard App Usage page — total duration shown is
         inflated when the same browser app has multiple open tabs

DESCRIPTION:
  When an employee opens a browser (Chrome, Edge, or Brave) with multiple
  tabs (e.g., 10+ tabs) and works actively for 2 hours, the App Usage page
  shows a total duration of 20+ hours instead of 2 hours.

  Example scenario:
    - User opens Chrome with 12 tabs
    - User works in Chrome for 2 hours (active focus)
    - App Usage page displays: "Chrome: 24 hours" or "Chrome: 20+ hours"
    - Expected: "Chrome: 2 hours"

  The duration shown is always approximately: (number of tabs) × (actual
  work time). With 10 tabs and 2 hours work, it shows ~20 hours.

STEPS TO REPRODUCE:
  1. Open Chrome (or Edge/Brave) with multiple tabs (at least 5-10)
  2. Actively use the browser for exactly 2 hours
  3. Navigate to the web dashboard → Employee Journey → App Usage
  4. Observe Chrome entry shows duration ≈ 2h × (number of tabs)

ROOT CAUSE:
  The browser journey tracker (`AccessibilityBrowserTracker`) creates one
  `app_sessions` row per browser window, but when multiple tabs are open
  in the same window, the system may be creating separate sessions per tab
  or counting each tab's activity independently.

  Possible root causes:
  a) The window key derivation does not properly group tabs under one
     browser window — each tab may get its own session key
  b) `foreground_seconds` / `background_seconds` are accumulated per tab
     rather than per browser window
  c) The flush logic (`FlushSessionFocusAsync`) may be running per-tab
     instead of per-window, multiplying the delta each cycle
  d) The `AccessibilityBrowserTracker` may not correctly identify that
     multiple tabs belong to the same top-level window process

  In the live DB, Chrome with 12 tabs open for 2 hours resulted in
  12 separate `app_sessions` rows (one per tab), each with 2 hours of
  foreground time, totaling 24 hours displayed.

AFFECTED FILES:
  - client/Core/AccessibilityBrowserTracker.cs (window/session key derivation)
  - client/Core/LogCollectorService.cs (flush logic, focus accumulation)
  - client/Core/ProcessCollector.cs (active window detection per cycle)

EXPECTED BEHAVIOR:
  All tabs within the same browser window should be grouped into ONE
  `app_sessions` row. The foreground/background accumulation should be
  per window, not per tab. When a user works in Chrome for 2 hours with
  10 tabs open, the App Usage page should show exactly 2 hours for Chrome,
  regardless of tab count.

  The duration should reflect real user activity time, not a mathematical
  product of tab count × work time.

FIX #8 — Group browser tabs under one window session, accumulate duration per window
---------------------------------------------------------------------------

  WHERE: client/Core/AccessibilityBrowserTracker.cs and
         client/Core/ProcessCollector.cs

  WHAT:

  1. IMPROVE WINDOW KEY DERIVATION:
     - `ResolveWindowKey` should merge all tabs belonging to the same
       top-level process (same ProcessId / exe name)
     - Use the AT-SPI role 95 (DOCUMENT_WEB) node's parent window ID
       to group tabs, rather than deriving a key per tab
     - Cache window identity per ProcessId for the session duration

  2. ACCUMULATE DURATION PER WINDOW (NOT PER TAB):
     - `foreground_seconds` and `background_seconds` should be tracked
       per window key, not per individual tab/session item
     - When a tab navigates, update the SAME window's session in place
       (ON CONFLICT DO UPDATE the window root), NOT create a new row
     - The poll interval delta should be added once per cycle to the
       window's totals, regardless of how many tabs changed state

  3. FLUSH LOGIC CORRECTION:
     - `FlushSessionFocusAsync` must flush per-window key, not per-tab
     - Ensure the in-memory dictionary key is the window identity, not
       the tab-specific key
     - On close, close the window session once, not each tab's session

  4. SESSION DEDUP ON BOOT:
     - `ReconcileStaleSessionsOnBootAsync` should detect and merge
       duplicate window sessions that belong to the same browser process
     - Keep only the earliest-created session row, close the rest

  WHY: Currently each tab or each focus change may be spawning a new
  session row or accumulating focus time independently. The fix ensures
  that ALL tabs of a browser window share one session, and the total
  focus time is the real user activity time — not tab-count × time.
