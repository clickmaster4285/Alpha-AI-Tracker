## Goal

A per-browser "Load Extension" action in the Avalonia UI — the user clicks it for each detected browser, one at a time (a one-time elevation prompt per click is accepted; see rev-3 pivot) — that:
1. Dynamically detects every installed browser per OS via OS-level registration — no hardcoded browser-name list gates detection, ever.
2. Attaches the existing MV3 extension via exactly **one of two** engine-scoped mechanisms — Chromium or Gecko — selected by the browser's actual profile-directory shape, never by its brand name. Persistent attachment uses the **elevated policy force-install path by default** (rev-3 pivot); the no-elevation `Preferences`-injection path is dev-fallback only (proven rejected on branded Chrome 137+/150).
3. Uses a **pure C# native messaging host** — zero Python in the shipped build.
4. Writes the `com.alphai.tracker.json`-equivalent native-messaging manifest per browser at the correct OS path, in the correct engine-appropriate shape (`allowed_origins` for Chromium, `allowed_extensions` for Gecko — never both, never guessed).
5. Degrades gracefully and honestly when a browser's engine can't yet be classified, or falls outside the two supported engines (WebKit) — never guesses, never silently drops it, always shows manual instructions instead.
6. Migrates existing installs off Python without breaking them mid-upgrade.

Status: Phases 1–4 are **implemented and validated** (see "Current state" and the phase plan). Phase 5 is now the **default persistent mechanism** (rev-3 pivot) but is **not yet implemented** — it is blocked on sub-phase 5A (self-hosted signed CRX) and, for Gecko, on the signed-`.xpi` workflow decision (see the research note). Phase 6 remains. This document is the living plan for the feature, not a proposal — it is updated as code lands.

## Engine-scoped implementation model (read first — governs every phase below)

This is the answer to "do I need 3 extensions / 3 codepaths, one per browser?" — **No.** The install mechanism is a property of the rendering engine, not the brand:

| Engine | Real browsers on it | Profile format | Manifest field | Install mechanism | Status |
|---|---|---|---|---|---|
| **Chromium** | Chrome, Chromium, Brave, Edge, Opera, Vivaldi, Arc, Opera GX, and any future Blink-based fork | `Preferences` JSON (`Local State` secondary signature) | `allowed_origins` (`chrome-extension://<id>/`) | **Policy forcelist (Phase 5 — THE default persistent mechanism, rev-3 pivot):** `ExtensionInstallForcelist` → self-hosted signed CRX + update-manifest XML (self-signed key, no Web Store publication; sub-phase 5A). `--load-extension` + `Preferences` injection demoted to dev fallbacks — the rev-3 real-Chrome-150 test proved branded Chrome rejects hand-injected `Preferences` (MAC-validated `Secure Preferences`). | **One implementation, parameterized by path only.** Identical manifest schema, identical extension-ID algorithm, identical profile JSON shape across every browser on this engine — only the config-dir path string differs per vendor. |
| **Gecko** | Firefox, Firefox ESR, LibreWolf, Waterfox, Zen Browser, and any future Gecko-based fork | `profiles.ini` + `prefs.js`/`user.js` (`compatibility.ini` secondary signature) | `allowed_extensions` (bare Gecko app id, e.g. `alpha-ai-tracker@alphai.com`) | Native host + manual `about:debugging` instructions (MVP) → `policies.json` `ExtensionSettings`/`install_url` to a **Mozilla-signed** `.xpi` (Phase 5, elevated). **Rev-3 research:** release Firefox hard-requires Mozilla-signed extensions; the `Preferences`-policy override of `xpinstall.signatures.required` is **ESR-only**; unsigned installs persist only on relaxed forks (LibreWolf/Waterfox). | **One implementation, parameterized by path + one flag** — signature requirement is channel-dependent: release Firefox = always required (Mozilla-signed `.xpi` only); ESR = policy-overridable; LibreWolf/Waterfox = relaxed by default. |
| **WebKit** | Safari, GNOME Web (Epiphany), other WebKitGTK browsers, Falkon (QtWebEngine — does not support Chrome-style extensions regardless of engine lineage) | N/A — no shared manifest.json/native-messaging-host-file model | N/A | **Structurally different, not implementable via this architecture.** Safari extensions since Safari 14 are native macOS/iOS App Extensions built in Xcode (Swift/Obj-C), signed and distributed via the Mac App Store or notarization. WebKitGTK has its own separate, much more limited C/GObject Web Extensions API with no `chrome.*`/`browser.*` compatibility layer. | **Explicitly out of scope.** This is not a "Phase 7 TODO" — it is a different product (a native Safari App Extension project, or a WebKitGTK extension project) requiring different languages and a different distribution model. Do not schedule it as a follow-up phase. If Safari support is ever needed, it is scoped as its own separate initiative, not an extension of this plan. |

**Practical consequence:** `BrowserEngineDetector` classifies every detected candidate into exactly one of `{Chromium, Gecko, Unknown}`. `Unknown` is not "WebKit support pending" — it is the correct, honest terminal state for (a) genuine WebKit-family browsers, (b) a Chromium/Gecko browser whose profile hasn't been created yet (first-run, no profile dir exists), or (c) any browser this heuristic genuinely cannot fingerprint. In all three cases the one-click flow shows manual instructions and never guesses which ladder to run.

## Rev 3 — Architecture pivot (2026-08-03, confirmed)

**Pivot (confirmed):** the one-click-per-browser flow means the employee is actively engaged with the tracker UI at the moment they click "Load Extension" for a given browser — so a **one-time elevation prompt (pkexec / UAC) per browser click is acceptable**. This is not a silent background operation. It matches the existing `MainViewModel.GrantLinuxPermissionsAsync()` pattern (pkexec for other permissions). Consequence: **Phase 5 (policy force-install) is promoted from "opt-in Advanced toggle" to THE default persistent mechanism for Chromium-engine browsers**, because the rev-3 real-Chrome-150 test proved the no-elevation `Preferences`-injection path is rejected by Chrome 137+/150 (`Secure Preferences` MAC validation) and cannot be made to persist.

**Per-click flow (the new default):**
1. User clicks "Load Extension" for one specific detected browser.
2. `Engine=Chromium`: elevate once (pkexec on Linux / `runas` UAC on Windows / System-Settings instructions on macOS) → write `ExtensionInstallForcelist` policy JSON pointing at the self-hosted signed CRX + update manifest → rewrite the native-messaging manifest → kill + relaunch that browser → poll heartbeat. Same UX shape as today, with the single elevation prompt inserted at step 1.
3. `Engine=Gecko`: equivalent `policies.json` write (elevated) pointing at a **Mozilla-signed** `.xpi` — see the research note below before finalizing this path.
4. `Engine=Unknown`: unchanged — manual instructions only, no elevation attempted.

**Firefox signing — decision-blocking research note (2026-08-03; sources: official Firefox admin reference `firefox-admin-docs.mozilla.org/reference/policies/`):**
- ❌ Release Firefox (non-ESR) does **not** honor disabling `xpinstall.signatures.required` via `policies.json`'s `Preferences` key. The official admin reference lists the preference as "(`xpinstall.signatures.required` — Firefox ESR 102.10, **Firefox ESR only**)" — the policy override is ignored on release builds.
- ❌ `ExtensionSettings` → `install_url` pointing at an unsigned/self-signed `.xpi` is rejected on release Firefox; signature verification is enforced against Mozilla's chain. (`temporarily_allow_weak_signatures`, Firefox 127+, covers only deprecated signature algorithms, not unsigned.)
- ✅ The viable enterprise path is a **Mozilla-signed `.xpi` obtained via AMO "unlisted" submission** (`web-ext sign` / `sign-addon` with AMO developer API credentials): Mozilla signs it, returns the `.xpi`, it is **never publicly listed** on AMO, and it can be self-hosted for `install_url` force-install. One-time workflow per extension version bump (re-sign on each bump).
- → **Decision blocked until the signed-`.xpi` workflow is set up:** Gecko Phase 5 cannot proceed with a self-signed `.xpi` on release Firefox. Either (a) accept the AMO-unlisted signing step as required infrastructure (sub-phase 5B), or (b) keep Gecko at "native host + manual instructions" on release Firefox and only auto-force-install on relaxed forks (LibreWolf/Waterfox) and ESR (policy override available there).

**Chromium signing — self-hosted CRX (no Web Store publication):** self-hosting a signed CRX for `ExtensionInstallForcelist` does **not** require Chrome Web Store publication. A self-signed private key + packaged `.crx` + a self-hosted update-manifest XML (`<gupdate>` with the extension ID, `codebase` URL, and CRX hash) is sufficient for enterprise policy force-install. This is separate infrastructure work — generate the signing key, package the `.crx`, host the update manifest (likely on the existing Go+PostgreSQL server hub) — scoped as **sub-phase 5A** before Phase 5 implementation starts (see Phase 5).

## Decision — pure C# native host: Option (b), the main client exe in `--native-host` mode

**Pick: (b) the `com.alphai.tracker.json` manifest `path` points at the main client executable, launched in a dedicated native-host mode.** (Implemented, Phase 1.)

Why (b) over (a) a standalone console exe:

| | (a) separate self-contained console exe | (b) main exe + CLI mode |
|---|---|---|
| Artifacts | New publish target + RID set + extra bundle step in `publish/build-installer.sh` | **None** — the existing self-contained publish already ships one exe per RID |
| Version skew | Host and tracker can drift | Impossible — same binary |
| Memory/start | ~small if trimmed/NativeAOT (adds build complexity) | Larger exe, but the browser spawns the host once per connection anyway |
| Elevation/entitlements | Separate signature/macOS entitlements to manage | Reuses the app's existing signing story |
| Mode detection | Manifest `path` can't carry args → must use argv-origin trick regardless | Same argv-origin trick (below) |

**The one real constraint on (b):** Chrome/Firefox native-messaging manifests allow only a single `path` string — the browser spawns the host with an identifying argument as `argv[1]`. Chromium passes the extension origin (`chrome-extension://<id>/`); Firefox passes the **bare Gecko application id** (`alpha-ai-tracker@alphai.com`, no URL-scheme prefix). So the host mode is entered by detecting that argument via the three-way check in Phase 1, plus an explicit `--native-host` flag for dev/manual testing (`dotnet run -- --native-host`).

**Critical ordering requirement in `Program.cs` (implemented):** the native-host short-circuit runs immediately after the existing `--encrypt-config` block and **before** `EnvLoader.Load()`, the `new Mutex(true, "AlphaAITracker", ...)` single-instance gate, the `Host.CreateApplicationBuilder`, and `BuildAvaloniaApp()`. A host process spawned by the browser never touches the mutex, the SQLite DB, or the DI container — it only does stdio ⇄ socket forwarding and exits. Confirmed unaffected by validation: normal `dotnet run` (no args) still launches the full Avalonia/DI startup.

Host mode behavior (mirrors `native-host.py` exactly, so `NativeMessageService` needs zero protocol changes):
- Read framed message from raw stdin (`4-byte native-endian length` + UTF-8 JSON, 1 MB cap — identical to `native-host.py: read_message()`).
- `action == "ping"` → forward to socket (so `NativeMessageService.IsExtensionConnected()` heartbeat updates), reply `{"status":"ok","detail":"pong"}`.
- Otherwise forward to a **fresh** Unix socket connection at the same path `NativeMessageService` computes (`~/.local/share/alpha-ai-tracker/native-messaging.sock`), read the response, write it back framed on stdout. Catch socket failures and reply `{"status":"error",...}` instead of crashing (mirror `forward_to_tracker()`).
- Loop until stdin EOF. Never instantiate Avalonia, never register in DI, never start services. On JSON parse error it writes an error frame and **continues** (parity fix from code review).
- **Orphan cleanup:** with (b) the host process shares the tracker's exe name, so `KillOrphanedNativeHostProcesses()` matches by command line (`--native-host`, `chrome-extension://`, or the Gecko application id in argv), never by bare exe name (which would kill the tracker itself).

Where the host code lives: `client/Core/NativeMessagingHost.cs` (a plain static runner, no DI), invoked from `Program.cs`. The socket path constant is centralized in `client/Core/NativeMessagingPaths.cs` (previously duplicated between `NativeMessageService` ctor and `BrowserExtensionService` ctor), along with the Gecko application id used for host-mode detection.

## What "attach" means per engine (real semantics + limitations)

**No browser supports live-attaching into an already-open instance.** Every mechanism below requires a browser restart; the one-click flow must either (a) kill + relaunch the browser (Chromium — the service already does this via `KillBrowserProcesses()` + relaunch) or (b) prompt the user to restart (Firefox / policy paths).

### Chromium family (Chrome, Chromium, Brave, Edge, Opera, Vivaldi)

| Mechanism | Persistence | Privilege | Restart | Viability as one-click default |
|---|---|---|---|---|
| `--load-extension=<dir>` (current Strategy 1, `TryLaunchWithLoadExtensionAsync`) | None — only that launched process; unpacked dev mode | None | Auto (service kills + relaunches) | **Dev fallback only.** Branded Chrome 137+ ignores the flag; Chrome 150+ blocks it. Fine for Chromium/Brave/Edge/Opera/Vivaldi. |
| **Profile injection** (`Preferences` JSON `extensions.settings[<id>].location=4`, current Strategy 2) | Yes — persists across restarts | None (user-profile file) | Auto (service relaunches) | **Dev fallback only (rev-3 demotion).** The real-Chrome-150 test (2026-08-03) proved branded Chrome strips the hand-edited entry (MAC-validated `Secure Preferences`) and never loads it. Still the right no-elevation fallback for Chromium/Edge/Brave builds that honor it. Generalized to per-browser `ConfigDir`/`DefaultProfileDir` (`~/.config/chromium`, `~/.config/BraveSoftware/Brave-Browser`, `~/.config/microsoft-edge`, `~/.config/vivaldi`, `~/.config/opera`). |
| **Enterprise policy `ExtensionInstallForcelist`** (managed JSON in `/etc/opt/<browser>/policies/managed/` etc.) | Yes — forced, survives everything | **Root** (pkexec) + browser restart | Auto (kill+relaunch inside the click) | **THE DEFAULT persistent mechanism (rev-3 pivot).** Self-hosted **signed CRX** + update-manifest XML — **no Chrome Web Store publication required** (self-signed key suffices for enterprise force-install). Needs sub-phase 5A infrastructure (signing key, `.crx` packaging, update-manifest hosting on the server hub). One elevation prompt per click is accepted. |

### Firefox (Gecko)

| Mechanism | Persistence | Privilege | Restart | Viability |
|---|---|---|---|---|
| Temporary add-on via `about:debugging` (current behavior) | No — gone on restart | None | Prompt | What the button does today. Honest fallback. |
| `policies.json` (`<firefox-install>/distribution/` or `/etc/firefox/policies/`) → `ExtensionSettings` + `install_url` to a **Mozilla-signed** `.xpi` | Yes — persistent, forced | **Root** | Prompt | **Release Firefox hard-requires a Mozilla-signed `.xpi`** (rev-3 research): the `Preferences`-policy override of `xpinstall.signatures.required` is ESR-only; self-signed `.xpi` is rejected. Signed via AMO **unlisted** submission (`web-ext sign`) — private, never publicly listed; one-time per version bump. Blocked pending the signed-`.xpi` workflow decision. |
| Native messaging manifest | n/a | None (`~/.mozilla/native-messaging-hosts/`) | n/a | Always install — needed for whichever attach path wins. |

**Firefox one-click default (rev-3):** install the native host manifest, launch Firefox, and show precise instructions (existing `ExtensionInstructions` flow) — release Firefox cannot persist an unsigned extension. Auto-persistent attach is gated on the Mozilla-signed `.xpi` workflow (Phase 5B) — call that out explicitly in the UI copy.

## Elevation handling (rev-3 pivot: one-time elevation per browser click is the DEFAULT)

**Pivot (confirmed):** because the employee actively clicks "Load Extension" for each detected browser one at a time, a **one-time elevation prompt per click is acceptable** — this is not a silent background operation, and it matches the existing `MainViewModel.GrantLinuxPermissionsAsync()` pkexec pattern. The elevated policy force-install (Phase 5) is now the default persistent mechanism for Chromium-engine browsers, since the no-elevation `Preferences`-injection path was proven rejected by branded Chrome 137+/150.

Still **no** elevation needed for (user-scoped, non-policy writes):
- Linux/macOS native-messaging manifests → `~/.config/<browser>/NativeMessagingHosts/`, `~/.mozilla/native-messaging-hosts/`, `~/Library/Application Support/<Browser>/NativeMessagingHosts/`.
- Windows → `HKCU\Software\<Vendor>\<Browser>\NativeMessagingHosts\com.alphai.tracker` (already implemented in `RegisterNativeHostWindows()`).

Elevation is required for the **policy write** in the per-click flow and reuses the existing, proven patterns:
- Linux: `pkexec bash <tmp-script>` — exactly like `MainViewModel.GrantLinuxPermissionsAsync()` / `InstallDependenciesAsync()`. Write the managed-policy JSON via a temp script so pkexec args stay clean; keep the `sudo -u $USER gsettings` trick for per-user settings. The client itself stays non-root (per AGENTS.md 2026-08-03: it runs as a systemd-user service / autostart — a root policy write is a one-shot elevated child process, not a change of the service's identity).
- Windows: `Verb = "runas"` UAC prompt — like `GrantWindowsPermissions()`.
- macOS: System-Settings instructions (no CLI elevation API) — like `ShowMacOSPermissionInstructions()`.

Ordering within the click (Chromium): elevate once → write `ExtensionInstallForcelist` JSON → write/refresh the native-messaging manifest → kill + relaunch the browser → poll heartbeat (same UX shape as today, with the single prompt inserted at the front).

## Phase plan

### Phase 1 — Pure C# native messaging host — ✅ Implemented & validated
- **`client/Core/NativeMessagingHost.cs` (new)** — static runner: framed stdin reader (4-byte LE length, 1 MB cap, UTF-8 JSON), framed stdout writer, per-message fresh socket forward to `~/.local/share/alpha-ai-tracker/native-messaging.sock`, ping special-case, error replies. Mirrors `native-host.py` 1:1 so `NativeMessageService` is untouched.
- **`client/Core/ExtensionIdCalculator.cs` (new)** — pure C# SHA-256(path) → a–p 32-char ID; verified byte-identical to the retired Python algorithm. Replaces the Python in `ComputeExtensionId()` / `InjectExtensionViaPython()`.
- **`client/Core/NativeMessagingPaths.cs` (new)** — centralizes the socket path constant (previously duplicated between `NativeMessageService` ctor and `BrowserExtensionService` ctor) plus the Gecko application id.
- **`Program.cs`** — native-host mode detection added immediately after the `--encrypt-config` block, before mutex/DI/Avalonia. Host-mode entry is recognized when ANY of the following holds (checked in order): (a) `argv[1]` starts with `chrome-extension://` — Chromium family (Chrome, Chromium, Brave, Edge, Opera, Vivaldi, and any detected Chromium fork); (b) `argv[1]` **exactly equals** the Gecko application id `alpha-ai-tracker@alphai.com` (from `browser_specific_settings.gecko.id` in `extensions/firefox/manifest.json`) — Firefox does NOT pass a `chrome-extension://` prefix; it invokes the host with the bare applicationId as `argv[1]`, so this clause is what recognizes Firefox and Gecko forks (LibreWolf, Waterfox, Zen Browser) that Phase 2 detects and Phase 3 gives manifests; (c) the explicit `--native-host` flag for manual/dev invocation (`dotnet run -- --native-host`). The framed-JSON protocol payload (read stdin → forward → write stdout) is identical in all three cases — only the entry-detection condition differs. Returns cleanly on exit.
- **`BrowserExtensionService`** — `InjectExtensionViaPython()` replaced with a C# `Preferences` editor (System.Text.Json on `extensions.settings`); `ExtensionIdCalculator` wired in; `InstallNativeHostAsync()` calls `InstallNativeHostManuallyAsync()` directly (the `install-extensions.sh` shell-out path was removed from routing); `KillOrphanedNativeHostProcesses()` matches by command line (`--native-host`, `chrome-extension://`, or the Gecko application id in argv), never by bare exe name.
- **Validated (real output):** build clean; `dotnet run -- --native-host` handled synthetic framed ping/navigate messages (pong reply + real `browser_tab`/`browser_navigation` rows persisted through the live `NativeMessageService`); Gecko-id argv and `chrome-extension://` argv both enter host mode; oversized frame → clean exit; malformed JSON → error frame and continue; normal `dotnet run` (no args) still launches full Avalonia/DI startup unaffected.

### Phase 2 — Dynamic browser detection per OS (registration-based, name-free) + engine classification — ✅ Implemented & validated, ⚠️ one gap proven (Brave path)
- `BrowserDetector.cs` / `BrowserEngineDetector.cs` implemented and validated as name-free.
- **Config-dir resolution (rev 2 fix):** `DeriveRoots` now uses a generic multi-candidate filesystem probe (BinaryName, DesktopId, stripped variants) instead of the `BrandCatalog` dictionary hint. The `BrandCatalog` class survives for display naming only (`(brandName, _)` discard in `ScanAsync`); it is structurally unreachable from path-resolution code.
- **⚠️ Proven gap (2026-08-03, simulated with a faithful populated `BraveSoftware/Brave-Browser` profile):** Brave resolves `Engine=Unknown`, `ConfigDir=''` — the probe's one-level correlated sweep never matches `BraveSoftware`, and no root is generated for `BraveSoftware/Brave-Browser`. Report-to-self: this is exactly the tradeoff the rev-2 plan flagged; the fix is a structural vendor-folder probe (two-level sweep or `<Vendor>Software/<Vendor>-Browser` pattern probe gated on a real `Preferences`/`Local State` hit), NOT a name-keyed shortcut.
- **Engine = Unknown (fail safe, not fail silent):** the browser still gets a `DetectedBrowser` entry and renders in the UI, but the one-click auto-attach ladder is skipped. The native-messaging manifest is also skipped (rev 2 fix — see "Open items" and the Bug fix notes below).
- **Validated (rev 2):** re-ran with Midori (unlisted Chromium-with-profile) → correctly classified Chromium, manifest written at `~/.config/midori/NativeMessagingHosts/`. Pale Moon (unlisted, no profile) → `Engine=Unknown`, no manifest written. ### Phase 5 — Elevation-backed policy install — THE DEFAULT persistent mechanism (rev-3 pivot); not yet implemented — ⚠️ blocked on sub-phases 5A/5B

Promoted from "opt-in Advanced toggle" to the default: the real-Chrome-150 test proved no-elevation `Preferences` injection cannot persist on branded Chrome, and the per-browser click flow makes one-time elevation acceptable.

**Sub-phase 5A — self-hosted signed CRX + update manifest (infrastructure, prerequisite for Chromium).**
- Self-hosting does **not** require Chrome Web Store publication: a self-signed private key, the packaged `.crx`, and a self-hosted update-manifest XML (`<gupdate>` with the extension ID, `codebase` URL, and CRX hash) are sufficient for enterprise policy force-install.
- Steps: generate the signing keypair → package the unpacked extension as `.crx` → host the `.crx` + update manifest (likely served by the existing Go+PostgreSQL server hub) → derive the extension ID from the public key (CRX-ID = first 16 bytes of SHA-256 of the public key — note this differs from the current path-derived ID, so `ExtensionIdCalculator` needs a second mode) → update native-messaging manifests' `allowed_origins` accordingly.
- Scope: standalone infra task with its own server endpoint; do **not** start Phase 5 implementation until this is reviewable.

**Sub-phase 5B — Firefox: signed `.xpi` workflow (decision-blocking, see Rev-3 research note).**
- Release Firefox hard-requires a **Mozilla-signed** `.xpi`; the `Preferences`-policy override of `xpinstall.signatures.required` is ESR-only; self-signed is rejected.
- Viable path: AMO **unlisted** submission via `web-ext sign` (AMO developer API credentials) → Mozilla-signed `.xpi`, never publicly listed → self-host → `ExtensionSettings` `force_installed` + `install_url` (elevated `policies.json` write).
- If the AMO-unlisted workflow is rejected for this product: Gecko stays at "native host + manual instructions" on release Firefox; auto-force-install only on relaxed forks (LibreWolf/Waterfox) and ESR (policy override available there).

**Per-click flow (the new default UX, Chromium):**
1. User clicks "Load Extension" for a specific detected browser.
2. Elevate once (pkexec / UAC) → write `ExtensionInstallForcelist` managed-policy JSON → write/refresh the native-messaging manifest.
3. Kill + relaunch that browser (existing `KillBrowserProcesses`/relaunch machinery) — policy picks up the CRX on launch.
4. Poll heartbeat (existing poller) → status flips to "✅ Active".
5. `Engine=Unknown` → manual instructions only, no elevation.

**Restart UX:** with the policy path, the click itself performs the kill+relaunch (same as today's Chromium behavior); no separate "restart required" prompt needed for the auto path.
