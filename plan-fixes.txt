# Fix Plan — Alpha AI Tracker (based on plan.txt diagnostic)

Scope: PROPOSAL ONLY. No code is implemented. Two sections:

  PART 1 — Quick, low-risk patches for Root Causes #1 and #2 (stopgaps).
  PART 2 — Two alternative architectures for Root Cause #3 (the real fix),
           with exact file-by-file impact and .desktop/systemd requirements.

Convention used below:
  [CHG]  modify an existing file
  [NEW]  add a new file
  [DEL]  remove an existing file (or mark dead)

================================================================================
PART 1 — QUICK, LOW-RISK PATCHES
================================================================================

--------------------------------------------------------------------------
1.1 ROOT CAUSE #1 — dotnetrunlog.txt written to root-owned install dir
--------------------------------------------------------------------------
Problem recap: Program.cs:65-66 writes the file logger to
AppDomain.CurrentDomain.BaseDirectory (= /usr/share/alpha-ai-tracker/ when
installed). FileLoggerProvider.cs:26 throws UnauthorizedAccessException for a
non-root user, before the try/catch at Program.cs:147, so the process dies with
no UI.

Patch 1.1a — relocate the log file (primary)
  [CHG] client/Program.cs (lines 65-66)
    - Compute logFilePath under a user-writable directory instead of BaseDirectory.
      Reuse the exact baseDir pattern already present at Program.cs:76-83
      (Linux: ~/.local/share/alpha-ai-tracker/ ; Windows: LocalApplicationData/
      AlphaAITracker/), i.e. the same directory the SQLite DB already uses, so
      the path is guaranteed writable and keeps all user data in one place.
    - Result: installed launches write dotnetrunlog.txt to the user dir — no
      crash, and dev-mode behavior is unchanged.

Patch 1.1b — make logger failure non-fatal (defense in depth)
  [CHG] client/Program.cs (around line 66)
    - Wrap `builder.Logging.AddFile(logFilePath)` in try/catch (Exception).
      On failure, write a single Console.Error line and continue building the
      host. Logging becomes best-effort; a bad path can never kill startup.
  [CHG] client/Services/FileLoggerProvider.cs (constructor, lines 20-28)
    - Guard the `new FileStream(...)` (line 26). On exception, construct the
      provider in a disabled state (null/no-op writer) instead of throwing.
    - Rationale: even if a future path regresses, the app must start.

Risk: negligible. No behavioral change for `dotnet run`; only moves the log
location and makes it optional. No .desktop/systemd impact.

--------------------------------------------------------------------------
1.2 ROOT CAUSE #2 — single-instance mutex blocks the GUI launch
--------------------------------------------------------------------------
Problem recap: Program.cs:39-45 uses a global named mutex "AlphaAITracker".
When the autostart/--background instance is already running (holds the mutex),
a second launch (app-menu .desktop, no args) exits immediately — no window.

Design of the patch: keep single-instance for the TRACKING role, but change the
GUI-intent launch from "exit" to "ask the running instance to show its window".
This is the standard single-instance-show-existing-window pattern and is the
seed of the IPC used in both architecture options in Part 2.

Patch 1.2a — tiny show-existing-window IPC
  [NEW] client/Core/SingleInstance.cs (small, ~100 lines)
    - `TryAcquire(string name, bool isServiceRole)`:
        * Primary (mutex acquired): spawn a background listener socket in the
          user config dir (Unix domain socket on Linux/macOS, named pipe on
          Windows — matching the existing cross-platform pattern in
          NativeMessageService.cs). Primary receives "show" and invokes a
          callback.
        * Secondary (mutex already held): connect to the socket, send "show",
          return false. No tracking, no window, exit cleanly.
    - Only the SERVICE role (--background/--minimized) takes the mutex.
      GUI-intent launches never contend for it at all — they either become the
      primary+show-window (nothing running) or signal+exit (service running).
      This already satisfies "open GUI while service runs".

Patch 1.2b — wire Program.cs
  [CHG] client/Program.cs (lines 37-45)
    - If launch is GUI-intent (no --background/--minimized): do NOT take the
      mutex / do NOT exit. Try `SingleInstance.Activate()` (signals existing
      window) and exit if it returns "another instance showed it"; otherwise
      proceed as the GUI process and register the Activate callback.
    - If launch is service-intent: take the mutex as today (prevents duplicate
      background tracking); on collision, exit silently (never show a window).

Patch 1.2c — wire the show callback
  [CHG] client/App.axaml.cs (around lines 20-91)
    - Register a handler so an incoming "show" from SingleInstance calls
      `mainWindow.Show(); mainWindow.Activate();` (and clears any minimized
      tray state). Reuse the exact logic of the existing tray
      "Show Alpha AI Tracker" item (App.axaml.cs:60-65).

Risk: low. Additive socket, no change to tracking loop or .deb packaging.
Caveat: the "running instance" is a tray-only process (--minimized), so
showing its window is exactly the intended behavior; no duplicate tracker.

Note — rejected alternative for 1.2: removing the mutex entirely. It would
allow duplicate background collectors writing the same SQLite file. Not
recommended as a "quick" patch.

--------------------------------------------------------------------------
PART 1 STATUS AFTER PATCHES
--------------------------------------------------------------------------
After 1.1 + 1.2, the CURRENT single-process design behaves acceptably:
  - First launch post-install: logger writes to user dir, window opens.
  - After login/reboot: autostart/--background instance runs headless;
    clicking the app-menu entry re-shows that window instead of dying.
  - Closing the window still only hides to tray (App.axaml.cs:43-50) — the
    target's "open/close/reopen without affecting the service" is only
    approximated here (close = hide). Full semantics require Part 2.

PART 2 — ALTERNATIVE ARCHITECTURES FOR ROOT CAUSE #3
================================================================================

Shared foundation (required by BOTH options, since the GUI must run in a
separate process from the tracking service):

  [NEW] client/Services/LocalIpcServer.cs
        - Runs in the SERVICE process. Unix domain socket on Linux/macOS,
          named pipe on Windows (mirror NativeMessageService.cs transport).
        - Command set (JSON): status, login-state, permission-state,
          pause/resume-tracking, quit, show-window (not needed by Option B
          GUI, harmless to include). Auth: per-user socket path in the user
          config dir (permissions 0700); no network exposure.
  [NEW] client/Services/LocalIpcClient.cs
        - Thin client used by the GUI process to call LocalIpcServer.
  [CHG] client/Services/BackgroundGuardService.cs (lines 93-103, 162-254)
        - Fix the chicken-and-egg: generate the user unit UNCONDITIONALLY on
          first service run (remove the `_systemdWasInstalled` gating at
          lines 93-103). ExecStart points at the service binary.
        - Make the unit headless-correct: with the service running headless,
          DISPLAY/XAUTHORITY (lines 178-179) are unnecessary; either drop them
          or derive from `loginctl show-session` (Wayland-safe). No hardcoded
          ":0".
  [CHG] client/ViewModels/MainViewModel.cs
        - GUI no longer touches SQLite/tracking directly. Replace direct
          _store / _logCollector / _autoStart / _browserExt calls with
          LocalIpcClient proxies (reads may stay local read-only; all writes
          and all tracking commands go over IPC).
  [CHG] client/Program.cs
        - See per-option DI split below.
  [CHG] client/Services/AutoStartService.cs
        - See per-option .desktop section below.
  [CHG] client/publish/build-deb.sh
        - See per-option packaging section below.
  [CHG] client/build.md
        - Update the systemctl instructions to the real, working unit.

Additionally, the Root-Cause-#2 mutex is re-scoped: it now guards ONLY the
service role (duplicate-background prevention). The GUI role never contends.

--------------------------------------------------------------------------
OPTION A — IPC-based single service + thin GUI (same binary, two modes)
--------------------------------------------------------------------------
Concept: ONE published binary (`client`). Mode selected by arg.
  - `--background` (systemd unit / autostart): service process. HostedServices
    + LocalIpcServer. Avalonia is NOT started (skip the
    `StartWithClassicDesktopLifetime` call entirely).
  - no args (app-menu .desktop): GUI process. Avalonia + MainViewModel +
    LocalIpcClient. Tracking HostedServices are NOT registered.

This keeps a single install directory and minimal packaging churn; the
process separation (service vs GUI) comes from the mode flag.

Files changed:
  [CHG] client/Program.cs
        - Split DI into two containers:
            Service container: SqliteLogStore, LogCollectorService +
              NativeMessageService + DesktopEventService (all the
              HostedServices today at lines 123-140), BackgroundGuardService,
              AutoStartService, LocalIpcServer.
            GUI container: MainViewModel, LocalIpcClient, HttpClient only.
        - `--background` path: build + StartAsync service container, wait on
          shutdown (CancellationToken), never call BuildAvaloniaApp().
        - no-args path: build + start service container ONLY IF none is
          already running (via SingleInstance), else connect GUI to the
          existing service; start Avalonia (line 154) with the GUI container.
  [CHG] client/App.axaml.cs
        - Unchanged conceptually (GUI mode only). ServiceProvider is the GUI
          container. Keep close-to-tray behavior (lines 43-50).
  [CHG] client/ViewModels/MainViewModel.cs   (see shared foundation)
  [CHG] client/Services/BackgroundGuardService.cs  (see shared foundation;
        unit ExecStart stays `{exePath} --background`)
  [CHG] client/Services/AutoStartService.cs   (see .desktop section)
  [CHG] client/publish/build-deb.sh           (see packaging section)

Files new:
  [NEW] client/Services/LocalIpcServer.cs
  [NEW] client/Services/LocalIpcClient.cs
  [NEW] client/Core/SingleInstance.cs  (service-role mutex, supersedes 1.2a)

.desktop / systemd unit generation for OPTION A:
  - App-menu .desktop (built by build-deb.sh:36-46):
        Exec=/usr/share/alpha-ai-tracker/client
      UNCHANGED. This now launches the GUI mode.
  - systemd user unit (generated by BackgroundGuardService, now unconditional):
        ExecStart=/usr/share/alpha-ai-tracker/client --background
        Type=simple / Restart=always / no DISPLAY (headless)
  - Linux autostart .desktop (AutoStartService.cs:209-220):
        Exec="{_executablePath}" --background     (was "--minimized")
      OR (recommended) drop the autostart .desktop entirely and rely solely on
      `systemctl --user enable alpha-ai-tracker.service` — avoids two startup
      mechanisms racing. Keep the autostart file only as a fallback for
      non-systemd sessions.

Trade-offs (OPTION A):
  + Zero new projects; one binary, one install dir; smallest packaging delta.
  + GUI cannot start tracking by construction (DI split) even though it ships
    in the same binary.
  - Service and GUI share the install dir; a fully "thin" GUI (no tracking
    code) is not achieved — payload size unchanged.
  - GUI/SQLite read path still needs care (read-only vs IPC) to avoid lock
    contention with the service (WAL + busy_timeout mitigates).

--------------------------------------------------------------------------
OPTION B — two-binary split
--------------------------------------------------------------------------
Concept: two published apphost binaries. Strongest separation.
  - alpha-ai-tracker-service: headless console binary. Tracking HostedServices
    + LocalIpcServer + BackgroundGuardService + AutoStartService. No Avalonia
    dependency at runtime.
  - alpha-ai-tracker-gui: Avalonia binary. MainViewModel + LocalIpcClient.
    Contains no tracking logic, no SQLite writes, no systemd/autostart.

Recommended layout: one new console project (service) + one new class library
(shared), so the GUI no longer ships tracking code.

Files changed:
  [CHG] client/client.csproj  — becomes GUI-only; drop tracking HostedServices
        and SQLite-write access from its DI/package refs (keep read-only or IPC).
  [CHG] client/Program.cs     — GUI-only entry (Avalonia + GUI container).
  [CHG] client/App.axaml.cs   — GUI only; ServiceProvider = GUI container.
  [CHG] client/ViewModels/MainViewModel.cs  (shared foundation — IPC-backed)
  [CHG] client/Services/BackgroundGuardService.cs
        — unit ExecStart becomes the SERVICE binary:
          ExecStart=/usr/share/alpha-ai-tracker/alpha-ai-tracker-service --background
        — unit generation made unconditional (fix lines 93-103).
  [CHG] client/Services/AutoStartService.cs
        — autostart entries (Linux .desktop / Windows Run key / macOS plist)
          point at the SERVICE binary, headless, with no window flags.
  [CHG] client/publish/build-installer.sh — publish both projects for each RID.
  [CHG] client/publish/build-deb.sh       — install both binaries (see below).

Files new:

        client.Service/Program.cs          (host + LocalIpcServer, no Avalonia)
  [NEW] client.CoreLib/                    — class library with the shared
        tracking/storage/config code, so the GUI binary no longer ships it:

        + moved (source-level) from client/:

          browser-scan results via IPC instead)

          Platform/{Linux,Windows,MacOS} collectors + detectors
          Configuration/{EnvLoader,AppConfig}.cs, Core/EncryptedConfigService.cs
  [NEW] client/Services/LocalIpcServer.cs  (service process)
  [NEW] client/Services/LocalIpcClient.cs  (GUI process)
  [NEW] client/Core/SingleInstance.cs      (service-role mutex)
  [DEL] (logical) tracking code removed from client/ — moved to client.CoreLib/
        so the GUI apphost has no reference to it.

.desktop / systemd unit generation for OPTION B:
  - App-menu .desktop (build-deb.sh:36-46):
        Exec=/usr/share/alpha-ai-tracker/alpha-ai-tracker-gui
  - systemd user unit (BackgroundGuardService, unconditional):
        ExecStart=/usr/share/alpha-ai-tracker/alpha-ai-tracker-service --background
        Type=simple / Restart=always / headless (no DISPLAY)
  - Linux autostart .desktop (AutoStartService.cs:209-220):
        Exec="/usr/share/alpha-ai-tracker/alpha-ai-tracker-service" --background
      (headless service; no window flags) — or rely on systemd only.
  - Packaging (build-deb.sh):
        /usr/share/alpha-ai-tracker/alpha-ai-tracker-gui      (Avalonia apphost)
        /usr/share/alpha-ai-tracker/alpha-ai-tracker-service  (console apphost)
        /usr/bin/alpha-ai-tracker -> .../alpha-ai-tracker-gui (symlink stays for CLI UX)
      postinst: unchanged except drop nothing (unit still generated at runtime).

Trade-offs (OPTION B):
  + Cleanest separation; GUI binary is genuinely thin; service cannot show UI
    and GUI cannot collect data by construction.
  + Smallest per-process attack surface and simplest reasoning about "service
    keeps running while GUI toggles".
  - Larger refactor: new projects, code migration into client.CoreLib/,
    two apphosts to publish and package; IPC layer required regardless.
  - Two .deb payloads to version/patch in sync.

  Lighter variant of B (if CoreLib extraction is deemed too large): skip the
  class library; make client.Service a console project that references
  client/ directly. It will carry Avalonia DLLs in its output (unused) but
  avoids moving any files. Trade-off: GUI and service binaries still both
  contain tracking + Avalonia code — separation is only at the process/entry
  level. Documented here as the pragmatic fallback.

============================================================================
RECOMMENDATION (decision aid, not implementation)
============================================================================
- Ship PART 1 patches first (1.1 + 1.2) — they are small, safe, and unblock
  the installed GUI immediately on the current single-process design.
- For Part 2, prefer OPTION A if the goal is low churn with correct behavior
  (one binary, mode flag, IPC thin GUI); choose OPTION B if binary payload
  separation / strict isolation between GUI and service is a hard requirement.
- Both options depend on the same LocalIpcServer/LocalIpcClient foundation;
  the Part-1.2 SingleInstance IPC is forward-compatible with both (it becomes
  the service-role guard).
- In both options, fix the systemd-unit chicken-and-egg
  (BackgroundGuardService.cs:93-103) and remove the hardcoded
  DISPLAY=:0/XAUTHORITY (lines 178-179); unit ExecStart must point at the
  SERVICE entrypoint, never a windowed launch.
