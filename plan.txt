WHY THE TIME-WINDOW HEURISTIC IS REJECTED
  - The 11 rows share an IDENTICAL nanosecond timestamp — that's "same poll
    cycle", not "started close together". A window solves a non-problem.
  - False merges: two genuine windows opened < 5s apart would collapse.
  - PPID/wall-clock are wrong keys because subprocesses get reparented and
    launchers exit before collection.
  Replacement: cgroup scope grouping (validated on the live system above).

CORRECTION 1 — Transaction sketch must not deadlock (BLOCKER, fixed)
═══════════════════════════════════════════════════════════════════════════
Actual store API (verified):
  StoreAppSessionsAsync(IReadOnlyList<AppSession>, CancellationToken)
  CloseAppItemsBySessionIdsAsync(IReadOnlyList<string>, DateTime, CancellationToken)
  BeginTransactionAsync(ct) → GatedTransaction (IAsyncDisposable) HOLDING the gate
Every public method acquires _connectionGate (SemaphoreSlim(1,1), NOT reentrant).
Calling two gated public methods inside one transaction = deadlock (second call
blocks on a gate the first is holding) — the class of bug this codebase already
avoids with private ungated helpers (SetStatusCoreAsync, GetEmployeeInfoCoreAsync).

FIX — one new composite store method, acquires the gate ONCE:
  // ILogStore
  Task CloseSessionsAndAppItemsAsync(IReadOnlyList<AppSession> closeSessions,
                                     DateTime closedAt, CancellationToken ct);
  // SqliteLogStore: gate once → one tx → 1) UPDATE app_sessions SET ended_at
  // 2) UPDATE app_items SET closed_at, is_synced=0 WHERE app_session_id IN (...)
  //    AND closed_at IS NULL → commit → release gate in finally.
True atomicity: a crash between the two writes is structurally impossible.

Wire it into ALL FOUR close paths:
  1. Main-loop normal close (line ~402) — TODAY IT DOES NOT CLOSE ITEMS AT ALL
     (verified) → this is exactly why the 11 orphans exist. PRIMARY FIX.
  2. ReconcileStaleSessionsOnBootAsync (~1467) — swap two calls for one.
  3. Garbage cleanup (~1586) — swap.
  4. Non-GUI cleanup (~1646) — swap.

CORRECTION 2 — No cycle-based key; keep PID fallback (BLOCKER, fixed)
═══════════════════════════════════════════════════════════════════════════
`{installedAppId}::cycle::{cycleId}` changes every poll → every unscoped process
recreated+closed each cycle → churn + sync spam. Rejected.

Two-tier key, BOTH stable across cycles:
  scoped:    "scope|{scope}|{installedAppId}|{machineId}|{clientSessionId}"
  unscoped:  "pid|{processId}|{machineId}|{clientSessionId}"   ← TODAY'S KEY, unchanged
installedAppId in the key: an app launched FROM a terminal inherits the
terminal's scope; scope+appId keeps them separate. Same scope + same appId
(11 VS Code PIDs) → ONE session. Different scopes + same appId (2 windows) → 2.

IMPLEMENTATION NOTES (NEW — do not miss these)
═══════════════════════════════════════════════════════════════════════════
N1. NO per-cycle dictionary. The real dedup mechanism is the persistent
    _previousSessionKeys + currentKeys maps. Make BuildSessionKey scope-aware
    and those maps dedup across cycles automatically. A throwaway
    "sessionsThisCycle" dict is redundant — and if you add it INSTEAD of
    changing BuildSessionKey, dedup only works within one cycle and every
    process gets a fresh session next cycle. There are exactly 6 call sites:
        LogCollectorService.cs lines 261, 295, 324, 503 (definition), 544, 569
    plus 5 _sessionRootItems uses (262, 310, 399, 544, 569). ALL must derive
    the SAME key, or context updates (UpdateActivityContextAsync) and closes
    will hit the wrong sessions.

N2. Keep the machine|clientSessionId suffix in the key (see Correction 2).
    Without it, keys collide across boots/machines.

N3. Scope must ride through the resolvedLogs tuple alongside
    displayName/appId/pkgId/isBrowser, and UpdateActivityContextAsync (which
    already receives appId) must also receive scope. Do NOT re-read
    /proc/<pid>/cgroup at 6 different places — resolve once per log, reuse.

N4. Boot hydration (line 261): GetOpenSessionRecordsAsync must add
    installed_app_id to the SELECT (new OpenSessionRecord field) and
    BuildSessionKey must live-resolve scope for still-running PIDs.
    Same-boot restart → process alive → scope matches → session reused.
    Cross-boot → process dead → PID fallback → stale session closed next
    cycle (existing behavior, correct). Verify this path during testing.
