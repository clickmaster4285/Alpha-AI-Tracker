# Diagnostic Plan — Installed Linux GUI does not open (alpha-ai-tracker .deb v1.0.0)

Scope: read-only analysis of `client/` source + `publish/` scripts. Nothing was
built, run, or modified. No fix proposed — only root-cause pinpointing.

================================================================================
0. PREMISE CHECK — "TWO SEPARATE RUN PATHS" DOES NOT EXIST IN THIS CODEBASE
================================================================================
The task premise says the install likely registers a systemd daemon + a separate
GUI process. The code shows the opposite: there is ONE binary, ONE process, ONE
entrypoint. Every launch path runs the identical code.

Evidence:
- Program.cs:37        `var isBackground = args.Contains("--background");`
- Program.cs:154       `BuildAvaloniaApp().StartWithClassicDesktopLifetime(args);`
  Avalonia is ALWAYS started, even with `--background` / `--minimized`.
- Program.cs:43        `--background` is only used to skip `Console.ReadKey()`.
- App.axaml.cs:84-87   `--background`/`--minimized` only suppress `mainWindow.Show()`.
  The tracking services (LogCollectorService, NativeMessageService, DesktopEventService,
  BackgroundGuardService) are HostedServices registered in Program.cs:124-140 and
  run in EVERY mode — GUI or not.
- The .deb ships a single binary `client` (build-deb.sh:23, .deb listing
  `./usr/share/alpha-ai-tracker/client`). No second GUI binary exists.

Consequence: "background service" and "GUI" are the same process. This alone
conflicts with the TARGET architecture (see findings below) and means the failure
to show a window post-install must be a startup-order crash or a single-instance
block, not a "wrong entrypoint launched" problem.

================================================================================
1. HOW Program.cs DECIDES BACKGROUND vs GUI
================================================================================
- Program.cs:15-33  `--encrypt-config` → build-time encryption, exits.
- Program.cs:37     `isBackground = args.Contains("--background")` — read but NOT
                    used to gate the GUI. Only gates the `Console.ReadKey()` at line 43.
- Program.cs:39-45  Named mutex `"AlphaAITracker"` — single-instance gate.
                    Second instance prints "Another instance is already running."
                    and RETURNS (exits). GUI is never reached.
- Program.cs:49-66  Host builder setup, including file logger (see Root Cause #1).
- Program.cs:154    GUI always starts.
- App.axaml.cs:83-87  Window shown UNLESS `--background` or `--minimized` present;
                    tray icon is created unconditionally (App.axaml.cs:54-81).

So: `--background` / `--minimized` = "start headless, tray-only". There is no
daemon-only entrypoint and no GUI-only entrypoint.

================================================================================
2. WHAT THE INSTALLER ACTUALLY INSTALLS / LAUNCHES
================================================================================
build-deb.sh (publish/) + the built .deb (inspected via `dpkg-deb -c`):
- Installs binaries + config.enc to `/usr/share/alpha-ai-tracker/` (root:root).
- build-deb.sh:36-46  writes `.desktop` file with
                      `Exec=/usr/share/alpha-ai-tracker/client` (no args, no %U).
- build-deb.sh:49     symlink `/usr/bin/alpha-ai-tracker -> /usr/share/alpha-ai-tracker/client`.
- build-deb.sh:73-99  postinst does NOT create any systemd unit, does NOT create an
                      autostart entry, and does NOT launch the app. It only: enables
                      GTK AT-SPI accessibility, `apt-get install xdotool`, refreshes
                      the desktop database.
- dpkg-deb -c output: NO `*.service` file is in the package. Confirmed.
- Nothing runs at install time. The first launch is the user clicking the
  app-menu entry → runs `/usr/share/alpha-ai-tracker/client` with NO args.

The systemd unit `alpha-ai-tracker.service` is generated at RUNTIME by
BackgroundGuardService.cs:162-254 (`ExecStart={exePath} --background`,
`Type=simple`, `Restart=always`, `Environment=DISPLAY=:0`). BUT it is only ever
written inside the watchdog when a unit was ALREADY detected on startup
(BackgroundGuardService.cs:93-103) — a chicken-and-egg loop on a fresh install.
It is effectively NEVER auto-created. The de-facto "background" mechanism on
Linux is instead the autostart .desktop written by AutoStartService.cs:202-226
(`Exec="{exePath}" --minimized`), enabled from MainViewModel.cs:215 and :584.

================================================================================
ROOT-CAUSE LIST (numbered, with confidence)
================================================================================

ROOT CAUSE #1 — UNHANDLED UnauthorizedAccessException writing dotnetrunlog.txt
                 to the root-owned install directory. The process dies before
                 any window can appear.
Confidence: CONFIRMED (deterministic from code; only assumption is a normal
            non-root desktop launch, which is the standard case).

File/line evidence:
- Program.cs:65      `logFilePath = Path.Combine(AppDomain.CurrentDomain.BaseDirectory, "dotnetrunlog.txt");`
  For the installed binary, `AppDomain.CurrentDomain.BaseDirectory` =
  `/usr/share/alpha-ai-tracker/`.
- Program.cs:66      `builder.Logging.AddFile(logFilePath);` runs during host
  setup — OUTSIDE the try/catch (try begins only at Program.cs:147). Unhandled.
- Services/FileLoggerProvider.cs:26  `new FileStream(path, FileMode.Append,
  FileAccess.Write, FileShare.Read);` — throws UnauthorizedAccessException when a
  non-root user opens FileMode.Append on a root-owned dir/file.
- .deb listing: `./usr/share/alpha-ai-tracker/` is root:root 775; binaries/files
  root:root. A desktop user cannot create/append a file there.
- WHY `dotnet run` works: BaseDirectory = `bin/Debug/net10.0/` (user-writable) →
  no exception → GUI opens. The ONLY meaningful path difference between dev-run
  and installed-run is this BaseDirectory write.
- WHY it looks like "nothing happens": the .desktop uses `Terminal=false`
  (build-deb.sh:42), so the crash trace goes to a discarded stderr.
- Side effects in the same root-owned dir that would ALSO crash once the logger
  is bypassed (for completeness):
  - BrowserExtensionService.cs:891-892 `_extensionsRoot` falls back to
    `BaseDirectory`; reads from `BaseDirectory/native-host.py` (read-only OK).
  - No other code WRITES to BaseDirectory except the logger at Program.cs:65.

ROOT CAUSE #2 — Named single-instance mutex blocks the GUI whenever a headless
                instance (autostart or systemd) is already running.
Confidence: CONFIRMED (mechanism), LIKELY (as the observed cause on sessions
            where a background instance is active). NOT the cause on the very
            first launch after install (nothing runs yet) — it compounds with #1
            and becomes the dominant cause after the first login + reboot.

File/line evidence:
- Program.cs:39-45  `new Mutex(true, "AlphaAITracker", out mutexCreated)` → on
  collision: prints and `return`s (exits) — before Avalonia init.
- AutoStartService.cs:213  autostart .desktop launches the SAME binary with
  `--minimized` at every desktop login. It holds the mutex for the whole session
  (headless, tray-only process that never exits).
- BackgroundGuardService.cs:173  systemd unit `ExecStart={exePath} --background`
  also holds the same mutex.
- MainViewModel.cs:215 and :584  `EnableAutoStartForced()` runs on every login →
  the autostart entry is written automatically after the first GUI login.
- Net effect matching the symptom: after login, the app is already running
  headless (mutex held); clicking the app-menu launcher
  (`/usr/share/alpha-ai-tracker/client`, no args) starts a SECOND process which
  immediately exits at Program.cs:45 → "GUI does not open."

ROOT CAUSE #3 — There is no GUI/daemon split at all; the architecture itself
                cannot satisfy the TARGET model.
Confidence: CONFIRMED.

File/line evidence:
- Program.cs:154  GUI always started; tracking HostedServices always started.
- App.axaml.cs:43-50  Window close is intercepted: `e.Cancel = true; mainWindow.Hide();`
  — the process stays alive (ShutdownMode.OnExplicitShutdown, App.axaml.cs:52).
- App.axaml.cs:60-65  The only way to re-show is the tray menu "Show Alpha AI
  Tracker" on the SAME process; a fresh launcher click is a different process
  and is blocked by #2.
- TARGET says: "background service must always run... GUI must be separate,
  toggleable, open/close/reopen any number of times without affecting the
  service." With one process + one mutex, closing the GUI is a hide (not a
  stop), and reopening cannot go through the launcher. Even after #1 and #2 are
  fixed, the TARGET architecture requires a real split (e.g., a second
  entrypoint or a mutex scoped per-role / IPC to show the existing window).

FINDING #4 — The systemd unit is effectively never auto-installed; the installer
             ships no service; docs claim systemd management that does not work.
Confidence: CONFIRMED.

File/line evidence:
- build-deb.sh:73-99 postinst creates NO unit, NO autostart, NO launch.
- dpkg-deb -c: no `*.service` file in the package.
- BackgroundGuardService.cs:93-103  unit is re-created ONLY if
  `_systemdWasInstalled` was true at startup (DetectSystemdService,
  BackgroundGuardService.cs:117-130) AND the file disappeared. Fresh install →
  never true → unit never written.
- AutoStartService.cs:85-95  `systemctl --user enable alpha-ai-tracker.service`
  is invoked with no unit file present → fails silently (exit code ignored).
- client/build.md:120-135 documents `systemctl --user stop/disable
  alpha-ai-tracker.service` — points at a service that is normally not installed.
- Practical consequence: the real "background" persistence is the autostart
  .desktop (`--minimized`) — which is exactly the process that later blocks the
  GUI via Root Cause #2.

FINDING #5 — Speculative edge-cases (do NOT explain the reported symptom, but
             relevant to the target architecture).
Confidence: SPECULATIVE.

- BackgroundGuardService.cs:178-179 hardcodes `Environment=DISPLAY=:0` and
  `XAUTHORITY=.../.Xauthority` in the unit. Under Wayland (this client supports
  Wayland — see AT-SPI code and postinst gsettings lines) `:0`/`.Xauthority` are
  often invalid, so if the unit ever launched a windowed mode it would fail to
  attach to the display. `--background` hides the window so it is non-fatal
  today, but it would sabotage the "open GUI from service" part of the target.
- BackgroundGuardService.cs:166 `Environment.ProcessPath` is captured at creation
  time. If the unit/autostart is ever created from a `dotnet run` dev instance,
  the ExecStart would point at `bin/Debug/net10.0/client` (a dev path), not the
  installed `/usr/share/alpha-ai-tracker/client`. Same applies to
  AutoStartService.cs:22-23 for the autostart .desktop.

================================================================================
3. PER-FINDING MATCH vs TARGET ARCHITECTURE
================================================================================
| # | Finding | Matches target? | Why |
|---|---------|-----------------|-----|
| 1 | dotnetrunlog.txt write crash | NO | Not architecture; pure packaging bug, but it currently PREVENTS any GUI/service from even starting, so the target is unobservable until fixed. |
| 2 | Single named mutex, whole-app scope | NO | Target needs GUI toggling independent of the always-running service. A global mutex makes a second (GUI) instance impossible. |
| 3 | One process runs service + GUI together; close=hide | NO | Target requires the service to keep running while GUI is closed/reopened via a separate launch. Current design can only hide/show one window in one process. |
| 4 | No real systemd install; autostart .desktop is the de-facto daemon | PARTIAL | Autostart does start on login (matches "always running"), but it is the SAME single-instance tray process, which then blocks the GUI (finding #2). |
| 5 | DISPLAY/XAUTHORITY + stale ProcessPath in generated unit | NO | Would break GUI-from-service under Wayland / after dev-mode first-run. |

================================================================================
4. WHAT IS NOT CERTAIN (explicit)
================================================================================
- Root Cause #1 is the strongest explanation for "dotnet run works, installed
  does nothing at all" and is deterministic from the code, but it was NOT
  empirically executed under this analysis (no run permitted). If the target
  machine's `/usr/share/alpha-ai-tracker` were somehow writable by the user, #1
  would not fire — then the sole cause would be #2 (background instance holding
  the mutex after the first login cycle).
- Whether the user actually performed a GUI login (which auto-creates the
  autostart entry, MainViewModel.cs:215/584) before observing the failure is not
  known; it determines whether #2 has already become active.
- Whether the systemd unit file already exists on the affected machine (e.g.,
  created manually per build.md) is not known; if present, `systemctl --user
  enable/start` would launch a `--background` instance that also blocks the GUI
  via the mutex.
