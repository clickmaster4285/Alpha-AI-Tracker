# GOAL 1 — Eliminate employee re-login (one-time login only)
# ════════════════════════════════════════════════════════════════════════

## 1.0 Problem statement
Client JWT (JWT_ACCESS_EXPIRY = 24h, server/internal/config/config.go:106) expires;
the client has NO auto-refresh. Syncs then return 401/403 (client/Services/SyncService.cs:518
logs + returns false) and data queues locally (is_synced=0) until a manual GUI re-login
that needs a NEW admin-generated one-time secret (Redis 5-min TTL, server/internal/redis/redis.go:13).

## 1.1 Decision — Option A: permanent device API key
- First GUI login mints a random 256-bit API key (never expires) for that employee.
- Stored server-side HASHED + in client SQLite employee_info (replaces token).
- Every sync sends apiKey instead of JWT. No re-login ever. Revocable per device.
- Backup options if rejected:
  - B: non-expiring employee JWT (config-only). Revocable only via global JWT_SECRET rotate.
  - C: device-binding (employeeId + machineId, no token). Weakest; machine_id is a
    per-user persisted GUID (client/Configuration/AppConfig.cs:124), NOT the MAC address.

## 1.2 Tasks (service-scoped, layering-explicit)

### T1.1 [server] employee_devices table + migration 021
- Layer: DB (migrations/021_employee_devices.sql) + repository (new_schema_repo.go).
- Contents: id, employee_id FK, machine_id, api_key_hash (NOT NULL, indexed),
  first_seen_at, last_seen_at, revoked_at, created_at. UNIQUE (employee_id, machine_id).
  Partial index for active keys (WHERE revoked_at IS NULL).
- Ship-Test: n/a (server) — go build / go vet; migration applied on a copy of the live DB.

### T1.2 [server] employee-login returns apiKey (auth flow)
- Layer: handler (auth_handler.go) -> service (auth_service.go) -> repository.
- Handler mints key on successful secret validation, upserts employee_devices, returns apiKey.
- JWT employee path becomes unused by the client but is NOT removed (fallback for Option B).
- Testing Strategy: table-driven test for login (valid secret, wrong secret, no Redis,
  revoked device). Test that re-login does NOT rotate the key (idempotent device).
- Ship-Test: go build / go vet, curl the endpoint.

### T1.3 [server] sync auth middleware (apiKey)
- Layer: middleware (new, per server/ARCHITECTURE.md layering) applied to the 11 sync routes
  in router.go. Validates api_key_hash against employee_devices; rejects revoked keys.
- Testing Strategy: integration test — valid key passes, revoked key 403, bad key 401.
- Ship-Test: go build / go vet; manual curl against each sync route.

### T1.4 [client] store + send apiKey
- Files: SyncService.cs (SendAsync payload), SqliteLogStore.cs (employee_info), AppConfig.
- employee_info.token column reused for apiKey (no schema change) OR new column via MigrateSql.
- [ASSUMPTION] token column reused to avoid a client migration; flag for confirmation.
- Testing Strategy: unit test that payloads carry apiKey; re-login keeps the same key.
- Ship-Test: build installer + dpkg -i; verify sync continues past 24h with no GUI.

### T1.5 [client] 401/403 handling
- On revoked-key 403: log once, STOP retrying that key, keep collecting locally.
- On 401 (bad key): continue exponential backoff (capped 60s, SyncService.cs).
- Testing Strategy: mock HttpClient returning 401/403; assert retry/stop behavior.

### T1.6 [web] device management UI
- Layer: web/src/lib/api.ts (new endpoints) + employees module page.
- View/revoke/rotate device key per employee (revoke = set revoked_at server-side).
- Testing Strategy: component tests for the revoke confirm dialog; API mock tests.
- Ship-Test: tsc --noEmit + next build.

### T1.7 End-to-end test
- First login -> syncs forever with no re-login; admin revokes -> device stops; re-login re-registers.

# GOAL 2 — DB architecture hardening
# ════════════════════════════════════════════════════════════════════════

### 2a. [server] Employee ID scalability ceiling  [P0]
- Problem: employee_id_seq MAXVALUE 99999 CYCLE (migrations/001_init.sql:9) -> UNIQUE
  collisions at ~90k employees (inserts fail after the sequence wraps).
- Fix: migration 022 — ALTER SEQUENCE employee_id_seq MAXVALUE 999999; verify nothing
  hardcodes the 5-digit EMP-XXXXX format (grep web input masks, validators, client).
- No-Hardcoded-Names compliance: none (structural).
- Testing Strategy: insert >99999 sequence values against a scratch DB; assert uniqueness.

### 2b. [server] Data retention / pruning job  [P0]
- Problem: no job deletes old app_sessions/app_items; unbounded bloat (AGENTS.md §5/§7).
- Fix: new jobs/retention_sweep.go (pattern: jobs/staleness_sweep.go) — config
  ALPHA_RETENTION_DAYS; delete app_items THEN app_sessions older than cutoff;
  children first (FK order). Client-side retention (24h) is independent.
- Testing Strategy: insert dated rows, run sweep, assert cascade order + FK safety.
- Ship-Test: go build / go vet; run against copy of live DB, verify row counts.

### 2c. [server] Dead / duplicate columns  [P1]
- Drop (migration 023, DROP COLUMN IF EXISTS): device_hardware_info.storage_devices (JSONB,
  superseded by storage_devices table), network_info.mac_address (client no longer sends),
  device_hardware_info.device_id (verify unused first).
- Verify NO Go SELECT/RETURNING references them (grep new_schema_repo.go) BEFORE dropping.
- Testing Strategy: migration on live-DB copy; assert app still boots and queries clean.

### 2d. [server] Single ownership model for installed software  [P1]
- installed_applications.employee_id / installed_packages.employee_id are legacy "first
  uploader" markers; junctions (015/016) are the real ownership. DECISION: keep columns
  but mark legacy in a comment + route all ownership queries through junctions. Dropping
  requires updating every repo query — defer unless audit shows zero usage.
- Testing Strategy: query audit — confirm no read path uses employee_id for ownership.

### 2e. [server] Referential integrity  [P2]
- app_sessions.installed_app_id/installed_package_id: no FK by design (013, out-of-order
  syncs). Keep as-is; document rationale in repo + ARCHITECTURE.md. No change now.

### 2f. [client] Token/API-key storage security  [P1]
- employee_info.token stored plaintext in SQLite. With permanent keys this is higher-stakes.
- Fix options: encrypt value with existing machine-key (client/Core/EncryptedConfigService.cs)
  at rest; or store key in encrypted config (config.enc) instead of SQLite.
- No-Hardcoded-Names compliance: MachineKeyPrefix must NOT be re-branded (AGENTS.md §6).
- Testing Strategy: unit test round-trip encrypt/decrypt; assert plaintext never on disk.

### 2g. [both] Schema drift  [P2]
- 11 mirrored tables kept in sync by hand. Add a documented schema-comparison checklist
  (no shared DTO today). Pure docs — no code.
