## 13. Browser Runtime Management (Self-Healing)

The new Browser Journey Engine must be self-healing.

It must automatically maintain browser tracking without requiring manual intervention.

### Browser Startup

Whenever the client starts (including after OS reboot):

1. Detect every installed browser.
2. Detect its browser engine.
3. Detect every installed profile.
4. Detect whether the browser is currently running.
5. Detect whether its debugging interface is available.
6. Detect which Browser Journey layers are currently active.
7. Restore the expected monitoring state automatically.

---

### Browser Debugger Management

The architecture must define a Browser Runtime Manager.

Responsibilities include:

* Detect whether Chromium debugging is active.
* Detect whether Gecko debugging is active.
* Detect whether WebKit remote automation is available.
* Detect active debugging ports.
* Detect disconnected debugger sessions.
* Detect browser restarts.
* Detect browser crashes.
* Detect debugger failures.
* Detect multiple browser instances.
* Detect multiple browser profiles.

The Browser Runtime Manager must explain how each browser engine should be monitored continuously.

---

### Automatic Recovery

If a browser is restarted:

The system must automatically determine:

* Is debugging already enabled?
* Is the debugger reachable?
* Is Browser Journey collection active?

If not:

Determine the safest supported recovery strategy for that browser engine.

The proposal must clearly distinguish:

* Fully automatic recovery
* Administrator-required recovery
* User-required recovery
* Unsupported recovery

Do not rely on undocumented hacks unless clearly identified as optional.

16. Browser Runtime Hierarchy (Mandatory)

The Browser Journey Engine must never identify browsers by process name alone.

Instead, the architecture must model the complete runtime hierarchy.

Browser Engine
    │
Browser Runtime
    │
Browser Profile
    │
Browser Window
    │

    │

    │

The architecture must explain:
