SECTION 0 — RULES THIS PLAN MUST OBEY
================================================================================

These come from AGENTS.md §6 and prompt.txt's "Core Directives" — restated
here so the plan is self-contained.

R1  Installer-Parity Rule (HIGHEST).
    A change is NOT complete until verified in an installed build
    (`bash publish/build-installer.sh -b linux && sudo dpkg -i ...`).
    `dotnet run` is for fast iteration only and cannot catch packaging gaps.

R2  No-Hardcoded-Names Rule.
    Software / OS event names MUST come from OS metadata, not product-name
    lists. The three "structural" wins we keep using:
      - Linux:  D-Bus interface names (org.freedesktop.UPower,
                org.freedesktop.login1, org.gnome.ScreenSaver)
      - Windows: Win32 API + WTS subsystem
      - macOS:   IOKit / NSWorkspace / CGEventSource
    No "If process name == 'logonui' then login" hacks. No "If window
    title contains 'Sign in' then login". The OS event IS the truth.

R3  Branding-Single-Source Rule.
    The product name and version come from ONLY:
        client/APP_IDENTIFIERS
        client/VERSION
    Any literal brand string or version number in any other file, XAML,
    or script is a bug to be fixed. This plan adds zero new literals.

R4  No-LocalStorage / Server-Projected Flags / Infinite-Scroll web rules
    apply to the Phase 2 web pages (out of scope here but flagged so the
    Phase 2 plan doesn't have to re-discover them).

R5  Single Source of Truth for new event types.
    New event_type strings ("power_on", "screen_lock"…) live in ONE
    constant in `client/Core/Models/SessionEvent.cs` with a doc comment.
    Server mirror lives in `server/internal/models/session_event.go`
    (or `status_tables.go`). The web renders them via the same constant
    set in a shared `web/src/lib/eventTypes.ts`. Cross-service drift is
    caught by an integration test (see §10).

R6  Path Discipline (AGENTS.md §6 "Installer-Parity Rule" item 6).
    The installed app's working dir is root-owned and unwritable. All
    runtime files use:
        Linux:   ~/.config/alpha-ai-tracker/  (config, logs)
                 ~/.local/share/alpha-ai-tracker/ (DB, sockets, cache)
        Windows: %LocalAppData%\AlphaAITracker\  (everything)
        macOS:   ~/Library/Application Support/AlphaAITracker/
    Never write to AppDomain.CurrentDomain.BaseDirectory on Linux.

2.3  New BackgroundService: SystemEventWatcher
     File: client/Services/Watchers/SystemEventWatcher.cs
     Pattern: copy the InstalledSoftwareWatcher shape (singleton +
     AddHostedService, debounce + min-gap, defensive try/catch around
     every event handler).
     Subscribes to:
        Linux:   UPower (PrepareForSleep), logind (PrepareForSleep,
                 Lock, Unlock), gnome ScreenSaver (ActiveChanged)
        Windows: Microsoft.Win32.SystemEvents.PowerModeChanged,
                 SystemEvents.SessionSwitch (ConsoleDisconnect/Connect,
                 RemoteDisconnect/Connect, SessionLock/Unlock),
                 WTSRegisterSessionNotification (defense-in-depth)
        macOS:   NSWorkspaceWillSleepNotification, didWake, screensDidSleep,
                 CGSessionCopyCurrentDictionary polling for screen lock
     Emits:  IEventRecorder.RecordAsync("power_on" | "power_off" |
              "resume" | "os_login" | "os_logout" | "screen_lock" |
              "screen_unlock")
     Guard rails:
        - All event handlers wrapped in try/catch (one bad event must
          not kill the watcher)
        - Events debounced 1.5s; screen_lock/unlock further guarded by
          a 30s hysteresis so a flaky screensaver doesn't write 50 rows
        - All events go through the new IEventRecorder abstraction
          (see §4) so the system event bus and the main collector
          funnel through the same store path
     Permission: screen-lock detection on macOS requires Accessibility
        permission; permission_status key updated so the existing
        "Pipeline healthy" check on the dashboard reflects it.

2.4  Idle / AFK detection (new module)
     File: client/Services/IdleDetector.cs
     Cross-platform:
        Linux X11: XScreenSaverQueryInfo (X11 lib via DllImport)
        Linux Wayland: /dev/input/event* open + EVIOCGKEYCODE poll
                       with input-grab. Fallback: idle = no process
                       has foreground focus (already partially
                       implemented in LogCollectorService's
                       foreground/background gate).
        Windows: GetLastInputInfo via P/Invoke (pattern exists
                 already for GlobalMemoryStatusEx at
                 LogCollectorService.cs:19-34)
        macOS: CGEventSourceSecondsSinceLastEventType
               (kCGEventSourceStateCombinedSessionState)
     Emits: IDLE_THRESHOLD_SEC cross -> writes "idle" markers via
            IEventRecorder. The server does not store a "raw idle"
            row; the client rolls up idle into daily_attendance_cache
            and the foreground/background focus system already covers
            in-session accounting.
     Thresholds (config-driven):
        ALPHA_IDLE_THRESHOLD_SEC         = 120   (when does "idle" start)
        ALPHA_IDLE_AWAY_THRESHOLD_SEC    = 600   (when does "away" start)
        ALPHA_IDLE_POLL_SEC              = 30    (poll cadence)

2.5  New IEventRecorder abstraction
     File: client/Core/Abstractions/IEventRecorder.cs
     Why: today the client has N call sites that all want to write
     session_events. Centralising them behind one interface gives us:
        - Debouncing policy in one place
        - Idempotency (same event ID won't double-write)
        - Local-then-sync ordering guarantees
        - Easy mocking for tests
     Contract:
        Task RecordAsync(string eventType, string? osUsername = null,
                         DateTime? at = null,
                         IReadOnlyDictionary<string,string>? meta = null,
                         CancellationToken ct = default);
        Task RecordBatchAsync(IEnumerable<SessionEvent> events, ...);
        Task<IReadOnlyList<SessionEvent>> PeekRecentAsync(int limit, ...);
     Implementation: SessionEventRecorder (wraps ILogStore +
        debounce + idempotency cache keyed on a 5-second window).
     DI: AddSingleton<IEventRecorder, SessionEventRecorder>()

2.6  Graceful-shutdown power_off emission
     Program.cs gets a small extension: a `ShutdownSentinel` singleton
     that hooks the IHostApplicationLifetime.ApplicationStopping event
     AND the Avalonia IClassicDesktopStyleApplicationLifetime.Exit
     event AND Console.CancelKeyPress. The sentinel calls
        await eventRecorder.RecordAsync("power_off",
                                        at: DateTime.UtcNow)
     inside a 2-second hard timeout. If the DB is locked (e.g. mid
     retention sweep) the sentinel logs and returns; we never block
     shutdown for telemetry.

2.7  Local time skew measurement
     Why: T&A aggregates by "local 09:00", not UTC 03:30. If the
     client clock is 4 minutes off, every "late by N minutes" number
     is wrong.
     One-shot: at every successful sync, log
        server_now - client_now
     into local_time_skew. Aggregated per server URL. Surfaced in
     Settings -> Tracking so admins can spot skewed machines.
     NOT auto-corrected (security antipattern — silent clock changes
     are a forensic-evidence nightmare).

SECTION 5 — SCALING (why this architecture survives 10k employees)
================================================================================

S1  Aggregated session_events sync.
    Today every lock/unlock = 1 row. A 9-to-5 employee with 50 lock
    events/day produces 50 rows synced. At 10k employees that's
    500k rows/day on the server just for locks. Fix: the new
    SessionEventRecorder groups events into 5-minute rolling buckets
    per (employee_id, event_type) before the SyncService drains.
    Each bucket row carries `count` + `first_at` + `last_at`. The
    server (Phase 2) reconstructs an event count for the dashboard.
    Net: 50 events -> 1-3 rows, depending on spread.
    Tunable via ALPHA_EVENT_AGGREGATION_WINDOW_SEC (default 300).

S2  Per-employee sub-batches in SyncService.
    Today all 11 tables drain in process-wide chunks. With T&A the
    session_events table becomes the biggest by row count. Change
    the drain loop to key on (employee_id, table) and run sub-batches
    in parallel via Task.WhenAll with a small parallelism cap
    (ALPHA_SYNC_PARALLELISM, default 4). Failure stays per-sub-batch
    so one employee's locked table doesn't poison the others.

S3  High-water-mark keys in app_status.
    Beyond last_heartbeat_at we now write:
       ta_last_schedule_pull_at
       ta_last_aggregator_run_at
       ta_last_skew_measure_at
    All keyed strings; cheap; index already exists. The Settings ->
    Tracking page can read them for the "what was the last thing the
    client did" view.

S4  Timezone column is per-employee, not per-row.
    Storage decision: we add `timezone` to employee_info (the existing
    table) rather than every event row. Aggregator uses the per-employee
    tz to bucket events into local workdays. 1 column vs 1B columns.

S5  Index strategy.
    Add on session_events: (event_type, event_at),
                          (employee_id, event_at)
    The AttendanceAggregator's daily-window reads become O(log n).
    The /session-events/sync drain uses (is_synced, event_at)
    (already partially covered by idx_session_events_unsent).

S6  Local cache is a hard ceiling, not a soft one.
    Cap on session_events rows in SQLite: ALPHA_TA_MAX_LOCAL_ROWS
    (default 50_000). Beyond that, the oldest UNSYNCED rows get
    rolled up into a single "old_data_dropped" sentinel row that
    IS synced, so the server knows. Same pattern as
    ALPHA_SYNC_RETENTION_HOURS today, but for the T&A edge case.

S7  ScheduleCacheService is pull-once, not push.
    Schedules change rarely (HR changes are a 9-5 admin task). The
    client PULLS /api/v1/schedules/me on login and every 6h, not
    via WebSocket. Push is out of scope for Phase 1.

S8  AttendanceAggregator runs at most every 5 minutes.
    Even on the client, a 30s cycle is overkill for "what was
    today's attendance status". 5 min is the sweet spot: the
    dashboard's "live" tile will lag by ≤5 min, which is honest
    given the underlying data is already 30s-granular.

SECTION 6 — SERVER-SIDE DEPENDENCIES (Phase 2 — flagged, not built here)

The Phase 1 CLIENT work below assumes the following SERVER endpoints
exist. If they do not, Phase 1 still builds and runs, but the
ScheduleCacheService and the Time-Skew measurement degrade to
no-ops. They are listed here so Phase 2 has a clean punch-list.

SVR-1  GET  /api/v1/schedules/me
       Returns the calling employee's current schedule + active
       holidays. JSON:
         {
           "timezone": "Asia/Kolkata",
           "graceMinutes": 10,
           "weeklyPattern": { "mon": "09:00-18:00", ... },
           "holidays":  [ { "date": "2026-12-25", "label": "Xmas" } ],
           "validFrom": "2026-01-01",
           "validTo":   null
         }
       Auth: same JWT cookie + device-token header the /sync
       endpoints use today.

SVR-2  POST /api/v1/session-events/sync (already exists per
       AGENTS.md §5 "11 sync endpoints")
       The C# mapper needs a small extension so a 5-min aggregate
       row (with `count`, `first_at`, `last_at`) round-trips. The
       server currently expects 1 row = 1 event.

SVR-3  GET  /api/v1/server-time
       Returns Date header + a JSON `nowUtc` field. Client
       compares to its own clock and records skew. Cheap.

SVR-4  GET  /api/v1/attendance/today?employeeId=…
       The web T&A dashboard reads this. Not a client dep but
       the server-side aggregator that backs it. Out of scope
       for THIS plan.

None of SVR-1/3 are required to merge the Phase 1 client work.
Phase 1 ships behind a feature flag (ALPHA_TA_ENABLED=true) and
the ScheduleCacheService and LocalTimeSkewService are
NO-OPS until their endpoints exist.

SECTION 7 — BUGS FOUND WHILE PLANNING (must fix in this phase)
================================================================================

These are bugs the planning read of the code surfaced. Each gets
fixed as part of the Phase 1 work; none are "discovered later".

BUG-1  Power-off time is unobservable.
       File: client/Services/LogCollectorService.cs (no power_off
       write anywhere)
       Repro: shut the PC down gracefully (Start -> Shut down).
       Open the dashboard. The last activity row is from minutes
       earlier; the dashboard shows "running" sessions forever
       (ReconcileStaleSessionsOnBootAsync eventually closes them
       on the next boot, but a 16h gap looks like a 16h session).
       Fix: ShutdownSentinel (§3 NEW, §2.6).

BUG-2  "login" is the only event_type ever written.
       File: client/Core/Models/SessionEvent.cs:131
       The doc comment lists "logout | lock | unlock" but no
       code path emits any. The model misleads future contributors.
       Fix: SessionEventTypes (§4) + LogCollectorService edit.

BUG-3  Window.Closing hides-to-tray without writing any event.
       File: client/App.axaml.cs:53-60
       When the user clicks the X on the window, the app goes
       to tray but no event is recorded. From the dashboard's
       perspective the employee is "active" forever.
       Fix: ShutdownSentinel covers this — the Avalonia
       Exit event fires when AllowShutdown is set, and the
       window.Closing handler now also calls the sentinel's
       light-weight "background" record (event_type = "ui_hidden")
       so the dashboard can distinguish "in tray" from "active".

BUG-4  Graceful shutdown via Ctrl+C is silent.
       File: client/Program.cs (the background-mode try/finally)
       A `kill <pid>` or Ctrl+C in the terminal tears down
       the host with no telemetry.
       Fix: Console.CancelKeyPress hook in Program.cs,
       delegates to ShutdownSentinel.

BUG-5  Schedule data exists only on the server.
       The T&A module is meaningless without "what was the
       employee's assigned shift today". The client has zero
       notion of a shift.
       Fix: ScheduleCacheService + new SQLite tables
       (employee_schedule, company_holidays) + new server
       endpoint (SVR-1).

BUG-6  Local clock skew is invisible.
       Today the dashboard shows "late by 5 min" using the
       client's local clock with no sanity check. A 4-minute
       skew is the difference between "late" and "on time".
       Fix: LocalTimeSkewService (§2.7) + new SQLite table.

BUG-7  No "is the OS event watcher actually running?" signal.
       The existing dashboard `IsSyncHealthy` is based on
       last_heartbeat_at. A stuck SystemEvents.PowerModeChanged
       subscription (rare but possible) wouldn't be visible.
       Fix: SystemEventWatcher writes
       `ta_last_known_os_event_at = DateTime.UtcNow` to
       app_status on EVERY received event, regardless of
       type. The dashboard's pipeline-health check then
       includes this in the tolerance window.

BUG-8  No idempotency on session_events writes.
       Two lock events from two sources within 1ms of each
       other (e.g. UPower + a screensaver) currently write
       2 rows. The aggregator will dedup them but the local
       store grows faster than necessary.
       Fix: SessionEventRecorder's 5s idempotency cache
       (§2.5).

SECTION 11 — RISK REGISTER
================================================================================

  R-MED  macOS Accessibility permission flow.
         If the user denies the prompt, SystemEventWatcher on
         macOS is silent. Mitigation: dashboard surfaces a
         "Permissions required" banner (existing pattern from
         PermissionSetupPage). Settings -> Tracking links the
         user to System Settings -> Privacy.

  R-MED  Windows WTS notifications require a window message
         pump. The new code must subscribe on the Avalonia UI
         thread, not a background thread, or the callback never
         fires. Mitigation: subscribe in App.OnFrameworkInitializationCompleted
         and unsubscribe in the symmetric shutdown hook.

  R-MED  systemd Stop signal on Linux might not give the
         ShutdownSentinel its 2s budget. Mitigation: write
         synchronously to a tiny "pending_events" file in the
         user config dir FIRST (1 syscall), then promote to
         SQLite on next boot. Belt-and-suspenders.

  R-LOW  D-Bus interface name drift on Wayland compositors.
         GNOME has org.gnome.ScreenSaver, KDE has its own.
         Mitigation: try a list of well-known interface names
         in priority order; the first one that responds wins.
         Log which one is active.

  R-LOW  LogCollectorService is the busiest single file in
         the project. Adding 3 more event writes risks
         coupling drift. Mitigation: ALL writes go through
         IEventRecorder. LogCollectorService never touches
         session_events directly.

  R-LOW  Daily attendance cache may diverge from the server's
         own aggregator (Phase 2). Mitigation: the cache is
         a presentation hint, not a source of truth. The
         server aggregator always wins. The cache is
         refreshed on every local event; the server side
         re-computes on read.

  R-LOW  R3 (Branding) violation risk: this plan adds a
         new app_status key prefix ("ta_") which is fine;
         do NOT add a new brand string. Audit before merge.

  R-LOW  R1 (Installer-Parity) violation risk: the new
         SystemEventWatcher uses only OS APIs that are
         already on the target machines. No new binary
         asset. If we later need an X11 helper (libXss),
         we MUST add it to bundle_into_publish() AND
         build-deb.sh AND build-dmg.sh AND
         installer-windows.iss. (No X11 on Windows; skip
         the .iss entry.)
